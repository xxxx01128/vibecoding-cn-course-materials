软件团队的代码评审要点

2015 年 2 月 9 日

代码评审是任何协作式软件项目中不可或缺的一环。大型软件系统通常由不止一个人编写，因此一支运转良好的软件团队需要一个稳健的流程，让成员以及代码库本身都朝着正确的方向前进。

代码评审是一个强大的工具，它能够：

  • 帮助团队成员随着系统的变化更新他们对系统的心智模型
  • 确保改动正确地解决了问题
  • 为讨论设计的优点与缺点创造空间
  • 在 bug 进入生产环境之前将其捕获
  • 保持代码风格与组织方式的一致性

把这些益处看作一个需求层次会很有帮助。

让团队成员保持一致

代码评审最关键的功能，是让团队中的每一位成员都朝着正确的方向前进。你无法安全地修改一个你不理解的系统，因此代码评审让团队在认知上保持一致。当 Bob 提交一个针对账务子系统的拉取请求时，Amy 在评审 Bob 代码的同时，更新了她对这个系统的心智模型。Amy 有机会就她不理解的部分提问，而 Bob 则受益于澄清自己的设计决策，同时也把他的工作讲给别人听。一个月后当 Amy 需要修改账务子系统时，她对这个系统的心智模型已经是最新的、随时可用。她花更少的时间读代码、在脑子里拼凑系统，而把更多时间用于思考更高层次的抽象与设计。每个人都赢了，因为大家都跟上了进度。

执行一个优秀的拉取请求

在你动笔写任何一行改动系统的代码之前，先问自己下面这些问题：

  • 「这是现在该做的事吗？」来自客户、内部团队成员和其他相关方的需求总是相互竞争。在深入投入之前，这是让优先级在你脑中保持清晰的好办法。其他流程，如迭代/冲刺计划会议，也有助于让事情保持在正轨上。
  • 「团队是否已经认同这个改动是正确的？」如果没有，最好先通过邮件或当面开启一场设计讨论。当人们在你改动之前就对设计达成一致时，你的改动更有可能被接受。
  • 「我如何把这个改动拆成易于评审和理解、可消化小块？」小的改动更容易思考和理解。良好的讨论源自团队能够快速理解你的改动。如果你的改动很大，队友们会看得眼神发直，你可能只会得到一些关于风格的小吹毛求疵。
  • 「我打算如何测试这个改动，以消灭 bug 并确保正确性？」你可能有质量保障（QA）部门，但交付高质量、可运行的软件仍然是作为开发者的你的职责。易于测试的软件通常耦合度更低、被拆成更小的块，也更容易推理。你需要为所有改动制定测试计划。

我发现，提前回答这些问题从长远来看为我省去了很多头疼事。你最不想做的，就是花几天时间写一个改动，最后却因为根本性的设计缺陷或团队意见不合而被否决。或者因为没人能验证其正确性而被卡住。同样，目标是在改动系统的同时，让其他团队成员跟上你的改动。问自己如何把工作拆成小块并测试这些小块，在很多方面都有帮助：

  • 它降低了风险
  • 它让改动更容易推理
  • 它推动你做出更好的设计

你更愿意用手术刀做许多小而精准的切口，而不是用砍刀砍出一道巨大的口子。在大多数增量式场景中，我更喜欢手术刀式的开发，而把砍刀留到该删除大块死代码的时候。

发送拉取请求

好，现在你已经获得了团队对你改动的认可，也实现了你原本设定的设计。真正发送拉取请求最有效的方式是什么？你一直在为改动努力工作，你希望团队其他成员关注你的拉取请求并快速给出反馈。你该怎么做？

还记得我之前说过的吗，代码评审最重要的部分是让团队的集体心智模型保持良好对齐。你的其他队友很可能在做与你完全不同的事情，也许在系统的完全不同的部分。他们的大脑处在完全不同的上下文中，所以你必须通过给他们提供做好评审所需的有用指引来克服这一点。这意味着要写一份条理清晰的说明，描述你做了哪些改动、为什么做这些改动，以及任何其他他们仅靠读代码无法获得的相关信息。不要让队友做不必要的脑力劳动。

让我们看几个拉取请求描述的好例子和坏例子：

坏例子：


Title: Fix uninitialized memory bug
Description:

This is the bug Bob and I talked about earlier. I had
trouble with the compiler but managed to make this work. Let me
know what you guys think.

如果你是这个拉取请求的开发者，停下来，把自己放在代码评审者的位置上想一想。标题含糊不清，引发的问题比给出的答案还多：内存 bug 在哪里？这个改动有多关键？你和 Bob 之前谈的是什么 bug？你在编译器上遇到了什么麻烦？这段描述既没有提供关于问题的有用上下文，也没有对你的改动给出有用的说明。如果这个拉取请求很长，评审者将不得不一头扎进代码里，在做任何关于这个改动如何融入系统连贯设计的思考之前，先费尽脑力去获取上下文。

这里有一个改进后的例子，有助于把变更集讲清楚：


Title: Fix process crash on startup from uninitialized memory [#54633]
Description:

This bug was causing process crashes on boot due to a memory
initialization error in our statistics Counter class. I talked this
over with Bob, and we both agree the crashes are a rare edge case
that don't warrant a hot-fix release. Here's a summary of the
changes:

  - Moved the underlying int variable into the class initializer
    to prevent ununitialized memory in the Counter.
  - Reworked the Counter interface to simplify caller conditional
    logic and prevent further off-by-one counting problems.
  - Added a unit test that exposes the crash

Testing: I've verified the test suite still passes, and verified
manually that the crash doesn't happen locally.

这个拉取请求描述有几处改进：标题的描述性足够强，能给评审者一些简短的上下文，并吸引他们点开邮件进一步了解。评审者知道这是进程崩溃（这通常是非常糟糕的事），而且还有一个 bug 报告编号，如果评审者想进一步了解问题，可以读到更多细节。新的描述还概述了问题发生在哪里，并帮助说明这个修复有多关键。有一份总结列出了拉取请求中的高层结构变化，让评审者在看代码之前就能在脑中形成改动的图景。代码评审者不应对他们看到的内容感到意外。这个例子还概述了所做的测试，让评审者确信这些改动经过了深思熟虑、充分测试，可以合并了。通过让评审者轻而易举地点击「合并」，来为他们的成功铺好道路。

评审者：给出建设性反馈

评审过程中接下来要考虑的部分，是向同伴给出建设性反馈。如果目标是清晰和对齐，那么给出高质量的建设性反馈能帮助每个人更好地理解系统，并推动代码变得更好。

避免说这样的话：

  • 「这个设计有问题。」为什么有问题？怎样能让它更好？这样的表述会伤害信心、让人难堪。
  • 「我不喜欢这个改动。」你为什么不喜欢？你希望改成什么样？不喜欢某样东西没关系，但你应该清楚地表达你的想法，并就代码如何改进提供有用的线索。
  • 「你能把这个重写得更清楚一点吗？」我现在写的有什么问题？我该怎么重写？哪里不清楚？这样的评论本身就含糊不清，没有给出一条简单的前进道路。

相反，要说这样的话：

  • 「这段代码如何处理负整数？」这条反馈很具体，会促使开发者自己思考各种结果。作为评审者，你可能知道相关代码在负整数时会崩溃，但更好的做法是让开发者自己推断出来。这样的问题也可能提示测试存在缺口，或需要进一步明确范围规格。
  • 「这一部分让我困惑，我不明白为什么类 A 要和类 B 通信」如果开发者没有提供有用的描述，而代码结构也不够整洁，这类评论有助于推动设计清晰化和代码更干净。
  • 「看起来你在这里打破了一个接口边界。这会如何影响用户？」你指出了你注意到的一个问题，同时相信他们是有意为之。现在他们可以思考打破接口边界所带来的看不见的连锁影响，要么为他们的决定提供理由，要么选择改动它。

总的来说，把反馈表述为提问是推动清晰性、正确性，同时帮助开发者在未来改进其设计的好方法。这通常是高质量的创意写作小组相互给出反馈的方式。在创意写作场景中，说「我不喜欢这个人物」是有害的，而同样的评论可以更清楚地重构为：「在第一章里你的人物温暖而富有同情心，现在他却冷酷无情。对我来说他不像个真实的人。」这样一来，就有了可以澄清、从而找出问题的具体反馈。

程序员喜欢解决问题、指出问题，所以他们天生喜欢发现并指出缺陷。很容易把代码评审当成一种通过在同伴代码里找问题来证明自己有多聪明的方式。不要这样做。代码评审是一种让更多人审视一个改动、找出关键问题的方式，但你的目标应该是以一种鼓励团队成员在解决手头问题的同时提升技能的方式来进行评审。

风格细节

花括号的位置、变量/函数命名、缩进和空格问题都应该处理，但它们并不是优秀代码评审的核心目的（注意我把它们放在代码评审金字塔的最顶端）。如果你发现团队花 90% 的时间在纠结缩进和变量名，那你们很可能把大家的时间浪费在本可以大部分自动化的事情上。写一份风格指南，在检入时强制检查缩进和空格问题，把你的时间集中在更高价值的问题上。我并不想贬低一致风格的重要性。恰恰相反，拥有一致且符合习惯的风格，是让你的代码库易于阅读和理解的最简单方法之一。尽管如此，如果你把所有代码评审的时间都花在这些琐碎任务上，问问自己是否是在回避那些更困难、更重要的工作——也就是让团队在认知上保持一致、思考更高层次的设计。
