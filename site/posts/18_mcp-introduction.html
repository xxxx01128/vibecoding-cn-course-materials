作者：Reed McGinley-Stempel

内容摘要

模型上下文协议（MCP）是一项开放标准，它在 AI 模型与外部数据和服务之间架起桥梁，使大语言模型（LLM）能够以一致、安全的方式发起结构化的 API 调用。本文将向读者介绍 MCP，解释它为何对连接 AI 系统如此有价值，把它与 ChatGPT 插件、手动 API 集成等现有方案进行比较，并深入探讨它近期对基于 OAuth 的身份验证的支持。我们还将研究一些代码，看看 MCP 的实际运作。

MCP 充当 AI 工具与外部服务之间的通用适配器，免去了为每个工具或 API 编写定制集成代码的需要。就像 USB-C 简化了各种不同设备之间的连接一样，MCP 为 AI 模型提供了一种统一的方法来调用外部函数、检索数据或使用预定义的提示词。MCP 的核心是用一个接口连接许多不同的系统。

什么是模型上下文协议 MCP？

MCP 本质上是 AI 应用与外部工具或数据源之间的一个通用适配器。它定义了一种通用协议（基于 JSON-RPC 2.0 构建），让 AI 助手能够以结构化的方式调用外部服务的功能、获取数据或使用预定义的提示词。每个大语言模型应用不再需要为每个 API 或数据库编写定制代码，MCP 为所有交互提供了一种标准化的"语言"。

MCP 层使 AI 应用能够安全地访问外部数据源和工具并与之交互。它充当大语言模型（LLM）与各种数据库、应用或 API 之间的桥梁，促进无缝集成和功能实现，而无需大量定制编码。

MCP 采用客户端—服务器架构来实现这一点。由 AI 驱动的应用（例如聊天机器人、集成开发环境（IDE）助手或智能体）充当宿主，并运行一个 MCP 客户端组件，而每个外部集成则作为一个 MCP 服务器运行。服务器通过 MCP 协议暴露各种能力（如函数、数据资源或提示词模板），客户端连接到服务器以利用这些能力。这种分离意味着 AI 模型不直接与 API 对话；相反，它要经过 MCP 客户端/服务器的握手，由握手来组织交换过程。

MCP 为何有价值

在传统的配置中，将 AI 模型连接到外部数据或操作是一项繁琐且临时性的工作。开发者往往不得不为他们希望模型使用的每个 API 或数据库编写一次性的集成代码，并分别处理不同的身份验证、数据格式和错误处理。MCP 通过标准化这些交互改变了这一局面。主要好处包括：

  • 快速工具集成：借助 MCP，你可以插入新的能力，而无需从头为每个能力编写定制代码。如果存在某个 MCP 服务器，比方说用于 Google Drive 或 SQL 数据库的服务器，那么任何兼容 MCP 的 AI 应用都可以连接到它，并立即获得该能力。这对自动化来说是一个巨大的胜利——AI 智能体可以根据需要获取文档、查询数据库或调用 API，只需添加相应的服务器即可。这就像拥有一个现成的"插件"库，它们都说着同一种语言。MCP 服务器充当轻量级程序，通过标准化协议暴露特定能力，在 Cursor 与各种外部工具或数据源之间充当中间人。
  • 自主智能体：MCP 赋予 AI 更强的自主行为能力。智能体不再局限于其内置知识；它们可以主动检索信息，或在多步骤工作流中执行操作。例如，一个复杂的智能体可能会使用 MCP 从 CRM 收集数据，然后通过通信工具发送电子邮件，再在数据库中记录一条记录——所有这一切都在一条无缝的链条中完成。通过支持流畅的、具有上下文感知的多步骤交互，MCP 帮助 AI 智能体更接近真正的自主任务执行。正如一位观察者所指出的，MCP 通过为 AI 提供对真实世界工具和数据的标准化访问，把 AI 从一个孤立的"大脑"变成了一个多才多艺的"实干家"。
  • 减少摩擦与配置工作：由于 MCP 充当通用接口，开发者避免了维护各自独立集成所带来的碎片化。一旦某个应用支持 MCP，它就可以通过单一机制连接到任意数量的服务。这极大地减少了每次想让 AI 使用新 API 时所需的手动配置工作。团队可以专注于更高层的逻辑，而不必第 10 次重新发明连接代码。正如 Anthropic 所说，MCP 用更简单、更可靠的单一数据访问协议取代了碎片化的集成。
  • 一致性与互操作性：MCP 在不同工具之间强制采用一致的请求/响应格式。这意味着你的 AI 应用不必为服务 A 处理一种 HTTP 响应，为服务 B 处理另一种 XML 响应，等等。模型的输出（函数调用）和工具结果都以统一的 JSON 结构传递。这种一致性使调试和扩展更加容易。它还使你的集成逻辑面向未来——即使你更换了底层模型供应商，MCP 与工具之间的接口保持不变。
  • 双向上下文：与简单的 API 调用不同，MCP 支持在模型与工具之间维护上下文和持续的对话。MCP 服务器除了提供工具之外，还可以提供提示词（针对某些任务的预定义提示词模板）和资源（如文档之类的数据上下文）。这意味着 AI 不仅可以"调用 API"，还可以摄取参考数据，或遵循由服务器引导的复杂工作流。该协议的设计初衷是支持丰富的交互，而不仅仅是一次性的查询。这在诸如编码助手（AI 可能通过 MCP 与开发环境反复交互）或需要与各种数据源来回交互的复杂决策任务等应用中尤其有用。

简而言之，MCP 为增强大语言模型带来了一种可扩展的、即插即用的方法。它让 AI 系统能够安全地接入它们所需的"实时"数据和操作，而每位开发者都不必重新发明轮子。MCP 的早期采用者已经为 Google Drive、Slack、GitHub、数据库等工具构建了服务器——展示了 AI 智能体如何使用 MCP 与企业内容仓库、DevOps 工具以及其他真实世界系统协同工作。

MCP 架构——一眼看懂其工作原理

客户端—服务器结构

MCP 遵循清晰的客户端—服务器架构：

  • MCP 客户端：嵌入在 AI 应用中（聊天机器人、集成开发环境助手、自动化智能体）。
  • MCP 服务器：暴露外部能力，如函数（工具）、资源（数据）和提示词（模板）。

所有交互都通过标准化的 JSON-RPC 消息进行，保持安全、结构化的交换：

JSON-RPC 请求示例：

例如，要列出可用工具，MCP 客户端会发送如下请求：


{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}
}

服务器将以结构化的 JSON 作出回复，列出这些工具（每个工具都有名称、描述和输入模式）。例如，服务器可能会公布一个 get_weather 工具，并描述它需要哪些输入。


{
  "jsonrpc": "2.0",
  "id": 1,
  "result": [
    { "name": "get_weather", "description": "Retrieves weather data.", "schema": { "location": "string" } }
  ]
}

之后，当大语言模型决定使用某个工具时，客户端会发起一次调用。MCP 服务器执行该函数，并在结构化的 JSON 响应中返回结果。MCP 客户端（位于宿主应用内）随后可以将该结果反馈回模型的上下文或响应中。在实践中，宿主应用负责协调这一过程：它将大语言模型的意图（通常通过模型的函数调用输出）转换为 MCP 请求，然后将服务器的结构化结果传回给大语言模型。这种双向交换是安全且受控的——模型只能调用服务器暴露的特定工具，所有进出的数据都要经过所定义的协议。

构建和部署 MCP 服务器

构建和部署 MCP 服务器是利用模型上下文协议（MCP）进行 AI 集成的关键一步。MCP 服务器充当 AI 模型与外部数据源或工具之间的中间人，实现无缝通信和数据交换。MCP 最突出的特点之一是它在服务器开发方面的灵活性。开发者可以使用任何能够向 stdout 打印或提供 HTTP 端点的编程语言，从而选择自己偏好的语言和技术栈。

在构建 MCP 服务器时，考虑架构和设计至关重要。MCP 遵循客户端—服务器架构，其中一个宿主应用可以连接到多个服务器。这种架构实现了可扩展性和灵活性，使开发者能够设计出处理各种任务和功能的 MCP 服务器，例如数据处理、工具集成或 AI 模型管理。

MCP 服务器可以部署在各种环境中，包括本地开发环境、云平台或本地自建基础设施。例如，Cloudflare 提供了一个强大的平台，用于构建和部署远程 MCP 服务器，使管理和扩展 MCP 部署变得更加容易。这种灵活性确保 MCP 服务器能够量身定制，满足不同应用和环境的特定需求，无论是用于开发的本地配置，还是用于生产的基于云的解决方案。

通过专注于设计良好的架构并利用 MCP 的灵活性，开发者可以创建强大且可扩展的 MCP 服务器，增强 AI 模型的能力，使其能够与外部数据源和工具无缝交互。

MCP 客户端与工具

MCP 客户端和工具是模型上下文协议生态系统的核心组件。MCP 客户端是连接到 MCP 服务器以访问外部数据源或工具的应用。这些客户端可以使用各种编程语言和框架来构建，例如 Python、JavaScript 或 Java，使开发者能够灵活选择最适合其特定需求的工具。

另一方面，MCP 工具是为 MCP 客户端提供特定能力或功能的软件组件。这些工具可以与 MCP 服务器集成，以实现数据处理、AI 模型管理或工具集成等功能。MCP 工具的例子包括 Claude Desktop（它提供一个与 AI 模型交互的聊天界面）和 Cursor（它提供一个用于扩展 AI 能力的插件系统）。

开发者可以构建自定义的 MCP 客户端和工具，以满足特定的用例或需求。这种灵活性为 MCP 生态系统中的创新和试验提供了空间，使开发者能够创建新颖而激动人心应用。无论是用于数据分析的专用工具，还是与多个 MCP 服务器集成的客户端应用，可能性都是巨大的。

通过利用 MCP 客户端和工具，开发者可以创建健壮且多用途的应用，充分发挥 AI 模型的潜力，使其能够与广泛的外部数据源和工具无缝交互。

让我们比较一下在 MCP 之前或与 MCP 同时存在的几种方案：

  • 自定义集成与 API 密钥管理：最传统的常见做法是为每项服务编写定制代码，并向大语言模型提供使用这些集成所需的凭据（API 密钥或词元）。例如，你可能会编写一个 Python 函数来查询 API，赋予大语言模型调用该函数的能力，并在后端手动处理 API 密钥。这种方法劳动强度大，而且无法扩展——每个新数据源都需要新代码，每个环境都必须安全地管理 API 密钥。它常常导致系统脆弱，因为每一项集成都是独一无二的。相比之下，MCP 集中并标准化了这些交互：AI 智能体只需处理 MCP 协议，任何 MCP 服务器（适用于任何服务）都能以即插即用的方式工作。添加新服务器时完全无需更改客户端代码。此外，MCP 为身份验证提供了一种正式的结构（稍后讨论），因此把 API 密钥交给 AI 不是以临时的方式进行的，而是通过一个安全的协议。
  • ChatGPT 插件（OpenAI 插件）：2023 年，OpenAI 为 ChatGPT 引入了一个插件系统，允许模型调用按 OpenAPI 规范定义的外部 API。这是迈向工具调用标准化的一步，但它有局限。每个插件本质上都是它自己的一个小型集成（有自己的 API 模式和身份验证），需要单独构建和托管。只有某些平台（如 ChatGPT 或 Bing Chat）才能使用这些插件，因为这是一种专有的做法。插件大多也是一次性的调用——模型调用 API 并获取信息，没有持久连接或持续的交互。MCP 的不同之处在于它是开放且通用的（不绑定到某个提供商或界面），并且支持丰富的双向交互和持续的上下文。可以把 ChatGPT 插件想象成封闭工具箱中的专用工具，而 MCP 是一个任何开发者或 AI 平台都能使用的开放标准工具箱。MCP 的标准化身份验证（尤其是 OAuth）也意味着它能以比 ChatGPT 系统中逐个插件的 OAuth 流程更统一的方式处理对用户数据的安全访问。总之，ChatGPT 插件展示了为 LLM 标准化 API 访问的价值，但 MCP 更进一步，使其成为开放协议，并实现 AI 与服务之间持续的"对话"。
  • 大语言模型工具框架（LangChain、智能体库）：在 MCP 出现之前，许多开发者使用 LangChain 之类的框架为模型提供工具。在这些配置中，你定义一组工具函数（附带描述）和智能体的提示逻辑，让大语言模型能够决定使用它们。这行得通，但每个工具在幕后仍然需要定制实现——LangChain 最终在其库中维护了数百个工具集成。从本质上说，LangChain 提供了一种面向开发者的标准（一个 Python 类接口），用于把工具集成到智能体的代码库中，但没有提供任何让模型在运行时动态发现新工具的机制。MCP 与这些框架是互补的，它把标准化转变为面向模型。有了 MCP，智能体可以发现并使用任何 MCP 服务器提供的工具，即使智能体的代码事先没有明确包含该工具。事实上，LangChain 已经增加了支持，可以将 MCP 服务器当作又一个工具来源——这意味着用 LangChain 构建的智能体可以轻松调用 MCP 工具，利用不断增长的 MCP 服务器生态系统。区别在于，MCP 通过协议（JSON-RPC，带有元数据等）将接口正式确定下来，使其更容易插入不同环境，而不仅仅是 Python 框架。类似地，OpenAI 原生的函数调用功能可以被视为处理函数调用的格式化（模型输出一个 JSON 函数调用），而 MCP 以标准化的方式处理该调用的执行。OpenAI 的函数调用和 MCP 经常协同工作：大语言模型产生一个结构化调用，MCP 客户端/服务器执行它并返回结果，二者共同实现无缝的工具调用。

从本质上说，MCP 并不是将大语言模型与外部 API 连接的首次尝试——但它借鉴了过去这些方法（插件、工具库等）的经验，并将解决方案统一起来。它提供了一种开放的、与模型无关的协议，简化了集成和身份验证。尤其是在安全性和身份验证方面，MCP 的设计（支持 OAuth）避免了逐个插件密钥的拼凑做法，也避免了把原始 API 密钥直接交给模型。相反，身份验证可以作为协议的一部分，以一致、标准化的流程来处理——这比现状前进了一大步。

MCP 实战：深入技术细节

让我们逐步走过一次典型的 MCP 交互，以巩固对其工作原理的理解，并看一些代码。假设我们有一个 AI 助手，它想使用一个提供一组工具的 MCP 服务器（比方说，用于一个假设的"Neon"数据库服务）。高层流程如下：

1. 连接到 MCP 服务器——宿主应用（AI 助手）初始化一个 MCP 客户端，并与服务器建立连接。根据服务器所在位置，这可能通过本地进程（stdio）或远程 HTTP 流（SSE）进行。在底层，客户端发送一条 initialize 消息来握手协议版本和能力。

2. 发现可用工具/资源——客户端随后查询服务器提供什么。如前所示，它可能会发送 {"method": "tools/list"} 并得到一份工具定义列表。助手可以用这些信息来告知大语言模型（例如，通过将工具列表包含在系统提示词中，或通过模型的函数模式，具体取决于实现方式）。例如，使用一个 SDK，这可能是一行代码，如：


const tools = await mcpClient.request({ method: 'tools/list' }, ListToolsResultSchema);

它返回一个结构化的工具列表。每个工具条目都有名称、描述和用于输入的 JSON 模式，让 AI 知道它能做什么。

3. 大语言模型选择工具——当用户向 AI 提出某个需要外部操作的请求时，大语言模型会判断（通常通过提示工程或函数调用能力）应该使用某个特定工具。例如，用户问："AAPL 股票的最新价格是多少？"大语言模型判断它应该调用 get_current_stock_price(company="AAPL", format="USD")。宿主应用捕获这一意图（例如，OpenAI 的函数调用 API 会以 JSON 形式返回函数名和参数）。

4. 通过 MCP 调用工具——客户端现在向服务器发送一个 tools/call 请求，带上所选的工具名称和参数。前面我们已经看到了相应的 JSON 示例。在代码中，使用一个 SDK，它可能看起来像这样：


const result = await mcpClient.request({
    method: 'tools/call',
    params: { name: toolName, arguments: toolArgs }
}, CallToolResultSchema);

这将使服务器在其一侧执行该工具的处理程序。服务器可能是在调用外部 API、执行数据库查询，或执行该工具封装的任何逻辑。结果（可能是一个简单的值，也可能是一个复杂的 JSON 对象）会在 MCP 响应的 result 字段中发回。

5. 将结果返回给大语言模型——MCP 客户端收到工具的输出。现在宿主应用可以把它整合回 AI 的响应中。在许多智能体配置中，做法是将结果注入对话，并要求模型继续。例如，助手随后可能会给出："AAPL 当前的股价是 173.22 美元（USD）。"如果使用自动化循环，结果可以交给模型（也许作为一条系统消息附加到对话中，如"get_current_stock_price 的结果：..."），模型便可以在牢记该信息的情况下继续回答用户的查询。

下面是一个简化的例子，展示如何调用工具并在对话中使用结果，这里使用 Anthropic 的 Claude（它原生支持工具调用）：


// 1. Send user prompt to LLM with available tools context
const response = await anthropicClient.complete({
  prompt: "User: Can you list my projects?\nAssistant: ",
  model: "claude-3.5",
  tools: tools // list of tools from MCP server
});
for (const msg of response.messages) {
  if (msg.type === 'tool_use') {
    // 2. LLM decided to use a tool
    const { name, args } = msg;
    // 3. Call the tool via MCP
    const toolRes = await mcpClient.request({ method: 'tools/call', params: { name, arguments: args } });
    // 4. Inject tool result and resume LLM
    await anthropicClient.send({ role: 'system', content: `Tool result: ${toolRes.result}` });
  } else {
    // 5. Handle normal LLM reply (tool result likely integrated)
    console.log("Assistant:", msg.content);
  }
}

在实践中，框架会为你处理其中的很多事情，但上面的伪代码勾勒出了 MCP 如何融入这个循环。关键之处在于，MCP 为工具执行提供了标准化的调用/响应层，AI 智能体代码可以接入其中。无论你使用的是 OpenAI、Anthropic 还是其他大语言模型，MCP 都保持不变——它是模型意图与外部操作之间的粘合剂。

通过使用 MCP，开发者获得了一条清晰、结构化的管道来扩展 AI 能力。代码变得更容易维护（因为你调用的是通用的 mcpClient.request，而不是在每个地方都写特定于服务的代码），AI 也变得更强大（因为它可以接入任何与 MCP 连接的服务）。调试也更加容易——你可以监控 JSON-RPC 消息，准确查看请求和返回了什么，而不必解析模型生成的文本来寻找线索。

早期的局限（无内置身份验证）

当 MCP 最初出现时（2024 年底），它提供了用于工具和数据交换的核心协议，但缺乏连接远程服务器的标准化身份验证机制。在实践中，早期的 MCP 演示和实现往往要求将 MCP 服务器运行在本地或受信任的环境中，在那里身份验证不是什么大问题（因为 AI 和服务器运行在同一台机器上）。例如，开发者可以在他们的 localhost 上运行一个用于 Google Drive 的 MCP 服务器，并使用预先获取的令牌，然后将他们的 AI 应用指向它。但是，如果没有正式的身份验证流程，通过互联网使用 MCP 或与第三方服务一起使用就很棘手。

许多早期的 MCP 服务器假定用户会在启动时手动向服务器提供凭据或 API 密钥。例如，Anthropic 的快速入门建议通过配置或命令行提供你自己的凭据（API 密钥、令牌）来运行预构建的服务器。这意味着服务器本身可以访问你的密钥，而 MCP 客户端只是信任该服务器。虽然这适用于个人或单用户场景，但对于多用户应用或云端托管的智能体来说，扩展性不佳。当时没有一种标准的握手机制，让 AI 智能体可以说："嘿，我被允许代表用户 X 访问这项服务；这是我的凭据。"

从本质上说，早期的 MCP 客户端除了通过带外方式（如预先共享令牌或在无身份验证的情况下运行）之外，没有办法向 MCP 服务器进行身份验证。这是一个值得注意的局限——MCP 本被设计为开放且基于互联网，但没有身份验证标准，安全的远程使用就受到了阻碍。

缺乏身份验证标准意味着 MCP 客户端无法自行安全地连接到任意服务器。你要么把客户端 ID/API 密钥硬编码到客户端中（这在分布式应用中并不理想），要么只能在没有身份验证的情况下运行，并假定只有授权用户才能访问服务器（通常是把它保持在本地）。显然，要让 MCP 发挥其全部潜力（例如以安全的方式将 AI 智能体连接到云端托管的数据源），需要一种更好的方法。好消息是，社区意识到了这一点，并且开展了工作，将基于 OAuth 的身份验证内建到 MCP 中。

OAuth 2.0 身份验证流程

为了解决最初的身份验证局限并增强安全连接能力，MCP 采用了 OAuth 2.0——一个得到广泛认可且健壮的身份验证标准。OAuth 2.0 提供了一个安全、可扩展的框架，使 MCP 客户端能够与远程服务器、云端托管资源和多用户环境安全交互。将 OAuth 2.0 集成到 MCP 中的关键组件和好处包括：

  • 动态客户端注册（DCR）：模型上下文协议支持动态客户端注册，允许客户端向 OAuth 服务器自动注册。这消除了手动配置客户端或硬编码凭据的需要，显著简化了开发者的部署工作。
  • 自动端点发现：MCP 利用标准化的元数据 URL（遵循 OAuth 的发现协议），使客户端能够自动发现 OAuth 端点。这减少了配置开销，使 MCP 部署更容易、更灵活。
  • 安全的授权与令牌管理：客户端安全地获取精确匹配用户权限和访问范围的 OAuth 令牌。这确保客户端只访问用户明确允许的资源，提高了安全性和合规性，尤其是在多用户和云环境中。
  • 可扩展且安全的多用户支持：OAuth 2.0 的设计天生支持多个并发用户和服务，解决了 MCP 早期的一个重要局限。应用现在可以同时无缝处理众多用户的授权流程，这对广泛的云采用至关重要。

调试与故障排查

调试与故障排查是使用 MCP 服务器和客户端时的关键环节。MCP 提供了各种用于调试和故障排查的工具与技术，确保开发者能够高效地识别并解决问题。这一过程中的一个关键工具是 MCP Inspector，这是一个用于 MCP 服务器的交互式调试工具。

MCP Inspector 使开发者能够测试和检查 MCP 服务器，识别并解决 MCP 服务器集成中的问题。该工具提供 MCP 客户端与服务器之间交互的详细视图，使定位问题和理解根本原因更加容易。此外，MCP 还提供了一份全面的调试指南，概述了常见问题和解决方案，帮助开发者快速排查和解决问题。

在调试 MCP 服务器时，考虑系统的架构和设计至关重要。开发者应当找出导致问题的具体组件或模块，并使用 MCP Inspector 之类的工具来诊断和解决问题。通过专注于系统化的调试方法并利用可用工具，开发者可以确保他们的 MCP 集成是健壮且可靠的。

MCP 的真实世界应用

模型上下文协议（MCP）在各个行业和领域都有多种真实世界的应用。MCP 的主要用例之一是 AI 集成，在这种场景下，MCP 实现了 AI 模型与外部数据源或工具之间的无缝通信和数据交换。

MCP 可以用于各种应用，例如：

  • 构建 AI 驱动的聊天机器人：这些聊天机器人可以访问外部数据源或工具，为用户提供准确且最新的信息。
  • 创建 AI 驱动的工作流：MCP 使 AI 模型能够与外部系统或数据源集成，自动化复杂的工作流并提高效率。
  • 开发 AI 模型：这些模型可以与外部工具或数据源交互，增强其能力，提供更准确、更相关的输出。
  • 实现 AI 驱动的自动化：在金融、医疗或制造等行业，MCP 可以自动化任务和流程，提高生产力并减少错误。

MCP 的灵活性和适应性使其成为开发者和组织在其应用中利用 AI 和机器学习的吸引人的解决方案。通过为 AI 模型提供与数据源和工具交互的标准化接口，MCP 为 AI 生态系统中的创新和试验提供了支持。这种标准化方法不仅简化了集成过程，还确保 AI 模型能够访问其发挥最佳性能所需的数据和工具。

总之，MCP 为 AI 应用开启了一个充满可能性的世界，使开发者能够创建更集成、更自主、更可扩展的解决方案。无论是用 AI 驱动的聊天机器人提升客户服务，还是在工业环境中自动化复杂的工作流，MCP 都提供了将这些创新变为现实所需的工具和框架。

结论

模型上下文协议（MCP）是 AI 开发中一项令人兴奋的进展，因为它让开发者能够安全、高效地将我们日益智能的语言模型连接到此前难以连接的广阔软件和数据世界。通过引入一种通用协议，MCP 使我们能够构建更集成、更自主、更易扩展的 AI 系统。我们不再需要为每个新工具编写一次性插件或给模型脆弱的指令，而是拥有一个连贯的框架，在这个框架中，AI 智能体可以在有适当监督和安全保障的情况下即时发现并使用工具。

尽管该协议仍在演进之中（身份验证是近期才加入的，更多功能如标准化的服务器发现也即将到来），但很清楚的是，MCP 或类似的东西将在下一代 AI 应用中发挥关键作用。对于开发者来说，现在是熟悉 MCP 概念的大好时机。无论你是用公司特定的知识来增强聊天机器人，还是构建一个自动化工作流的 AI 智能体，MCP 都能通过处理工具集成的"管道工作"为你节省时间和免去麻烦。而且，由于它是一个开放标准，背后有不断增长的社区（以及像 Anthropic 这样的公司）的支持，它很可能在未来成为 AI 基础设施的一块基石。

总之，模型上下文协议开创了一个世界：在这个世界里，AI 助手不再是彼此孤立的天才，而是装备精良的工程师和助理——能够与多个系统对接、遵循流程，并根据需要获取或创建信息，所有这一切都通过一个统一、安全的接口完成。这是一个强有力的愿景，而借助 MCP，它正在迅速成为现实。
