SAST 与 DAST 与 RASP：比较应用安全测试方法

学习2024年12月18日Shanika Wickramasinghe全球信息安全支出预计到2025年将达到 2120 亿美元。这较 2024 年增长了 15%。据 Gartner 称，生成式 AI和云采用的兴起是这一快速增长的关键原因。该分析机构进一步预测，到 2027 年，GenAI 将参与到 17% 的网络攻击之中。

企业需要超越传统方法的高级安全策略，以应对这些日益增长的威胁。正因如此，企业主有必要了解 SAST、DAST 和 RASP 这类安全解决方案，它们能为应用提供多层次的保护。

（相关阅读：应用安全详解和常见软件测试方法。）

什么是 SAST？

静态应用安全测试（Static Application Security Testing，SAST）是一种白盒安全测试方法。SAST使用应用的静态源代码或二进制文件来识别漏洞。这意味着 SAST 工具在应用未运行时对其代码进行操作。

开发人员使用 SAST 检测各种安全风险，例如代码中的跨站脚本（XSS）、不安全的反序列化、缓冲区溢出以及其他 OWASP 漏洞。由于仅靠 SAST 无法识别特定于运行时的漏洞，开发人员常常需要将 SAST 与其他测试方法结合，以实现全面的安全性。

SAST 是软件开发生命周期的重要组成部分，因为它能及早发现漏洞。越早发现漏洞，修复成本就越低。由于 SAST 工具可以在开发阶段执行，开发人员现在能够在产品发布到市场之前编写并测试代码，甚至多达一千次（！！）。

SAST 可以集成到持续集成/持续交付（CI/CD）流水线中，集成后即被称为「安全 DevOps」或「DevSecOps」。SAST 可通过自动化大规模扩展。能够实现涵盖 SAST 技术的自动化测试，使其成为快速应对代码级风险的高效方案。

什么是 DAST？

动态应用安全测试（Dynamic Application Security Testing，DAST）是一种黑盒测试方法。DAST 中的「动态」一词表明，该方法是在应用运行时评估其安全性。与 SAST 不同，DAST 不需要访问应用的源代码。相反，它会：

  • 模拟外部攻击者的行为。
  • 从外部测试应用，以识别仅在运行时才会出现的漏洞。

DAST 能够识别各种安全缺陷，如拒绝服务（DoS）漏洞和不安全的服务器配置。通过模拟真实世界的攻击场景，DAST 工具评估应用如何应对这些模拟威胁。借助这种方法，开发人员可以发现像 SAST 这样的静态测试方法可能遗漏的弱点。

通常，开发人员在软件开发生命周期的后期执行 DAST，往往就在部署之前。通过在真实环境中测试应用，DAST 清晰地呈现运行时安全状况，并支持构建性能更好、能够抵御潜在攻击的应用。

SAST 是如何工作的？

开发人员使用SAST 工具应用预定义规则及其他检测方法（如模式匹配和数据流分析），以识别编码错误和其他漏洞。他们将这些工具集成到集成开发环境（IDE）或持续集成/持续交付（CI/CD）流水线中，在编码和测试阶段自动执行扫描。

常见的 SAST 方法

以下是 SAST 中使用的一些方法。

模式匹配扫描代码库中已知的不安全编码实践模式。例如，使用弱加密算法或不安全的 API 调用。

数据流分析跟踪数据如何在应用中流动。通过追踪不可信输入到敏感操作的路径，可以识别SQL 注入或缓冲区溢出等漏洞。

控制流分析可以分析应用的控制结构。例如，分析循环和条件语句，以发现逻辑缺陷或竞态条件等潜在漏洞。

自定义规则创建。许多工具允许开发人员创建自定义规则，以遵循编码最佳实践。以下是这些自定义规则的一些示例：

  • 标记 SQL 查询中任何使用未经清理输入的情况。
  • 识别将用户提供的数据未经适当转义就输出到浏览器的代码。
  • 突出显示使用存在漏洞或已弃用的函数，例如 JavaScript 中的 eval() 或 C 中的 strcpy()。
  • 检测源代码中出现的硬编码 API 密钥和密码，并标记任何对用户提供的数据缺少输入验证的情况。

依赖扫描。一些 SAST 工具会分析应用中使用的第三方库和框架，以识别依赖项中的漏洞。

语义分析。通过解释代码的含义而非仅仅分析其结构，SAST 工具可以检测不安全的配置或 API 的误用。

机器学习模型：高级 SAST 工具引入机器学习算法，通过分析大型数据集中的模式来识别此前未知的漏洞。

使用 SAST 工具时的性能考量

SAST 工具通常需要大量 CPU和内存资源。在分析大型代码库时，这可能成为一个主要问题。对一百万行代码进行完整扫描可能会消耗数 GB 的 RAM。

SAST 扫描所需的时间会因代码库规模而差异巨大，从小型项目的几分钟到企业应用的数小时不等。这可能影响：

  • 构建流水线的时间安排
  • 开发人员的工作效率

考虑使用支持增量扫描的现代 SAST 工具，这样你只需分析发生变更的代码，而不必扫描整个代码库。

此外，通过选择规则和定义范围来进行性能调优至关重要。配置不佳的 SAST 工具可能会不必要地分析非关键代码路径，浪费时间和资源，却无法带来安全收益。

DAST 是如何工作的？

DAST 工具通过模拟真实世界的攻击（例如，向输入字段发送各种形式的恶意数据，观察应用如何处理），来识别应用行为和响应中的漏洞与弱点。

DAST 的步骤

该过程通常包括以下步骤。

第 1 步：扫描。扫描 Web 应用以发现入口点（如 URL、表单和 API）。此步骤会勾勒出应用的结构，并识别潜在攻击面。

第 2 步：攻击模拟。通过向应用发送精心构造的请求来模拟恶意活动。这些请求通过尝试利用入口点，检测跨站脚本和跨站请求伪造等漏洞。

第 3 步：漏洞检测。分析应用的响应以识别安全弱点。它评估应用在受到攻击时是否按预期运行。例如，可以注入恶意数据来检测 SQL 注入漏洞。

第 4 步：报告。生成包含检测到的漏洞及修复建议的报告。开发人员可以利用报告中的结果修复已识别的问题。

现代 DAST 解决方案可以融入 AI 驱动分析和实时数据集成等高级功能。它们会自动创建测试集，根据应用的结构动态调整，并利用机器学习算法尽量减少误报。

使用 DAST 工具时的性能考量

使用 DAST 工具时，需要牢记以下某些性能瓶颈。

  • DAST 工具会与正在运行的应用主动交互，暂时增加应用服务器和 Web 服务器的 CPU 与内存使用量。
  • DAST 扫描期间产生的大量并发请求会消耗大量网络带宽。
  • DAST 扫描器常常通过生成独特的请求来绕过或使应用缓存失效，从而降低缓存机制的有效性。
  • DAST 工具创建和管理多个测试会话，可能会增加应用服务器的内存使用量。

为避免此类问题或尽可能降低其影响，请遵循以下做法。

  • 将 DAST 扫描安排在应用使用量最低的非高峰时段。
  • 在与生产环境配置相同的预发布或准生产环境中进行扫描。
  • 使用 DAST 工具中的限流功能控制同时发出的请求数量。
  • 在扫描期间增加应用服务器的线程池。
  • 为 DAST 扫描器的 IP 配置单独的缓存策略。
  • 在超过性能阈值时实施自动暂停扫描。

SAST 与 DAST：关键区别

下表总结了 SAST 与 DAST 之间的区别。

标准

SAST

DAST

测试类型

白盒测试。在可访问源代码的情况下，由内向外测试应用。

黑盒测试。在无法访问源代码的情况下，由外向内测试应用。

支持的软件类型

支持多种类型的软件，包括 Web 应用、Web 服务和胖客户端。

支持 Web 应用和 Web 服务，但通常不支持其他软件类型。

软件开发生命周期中的阶段

在软件开发生命周期的早期执行。

在软件开发生命周期的后期进行，通常在部署期间或之后。

检测到的漏洞

识别编码缺陷，例如：SQL 注入、跨站脚本（XSS）、缓冲区溢出等。

检测运行时问题，例如服务器配置错误、拒绝服务漏洞和应用层缺陷。

修复漏洞的成本

成本较低，因为问题在软件开发生命周期早期就被发现。

成本较高，因为漏洞发现较晚，往往需要紧急修复才能按时部署。

运行时与环境问题

无法检测特定于运行时或与环境相关的漏洞。

可以识别仅在运行时出现或由环境因素导致的漏洞。

深度与广度

深入洞察代码级漏洞。

提供应用外部安全风险的广泛视图。

与工具的集成

与集成开发环境（IDE）和持续集成/持续交付（CI/CD）流水线集成，实现自动化静态分析。

与持续集成/持续交付（CI/CD）流水线集成，实现持续的运行时测试。

误报与漏报

由于深入的代码分析，误报的可能性更高。

误报较少，但由于内部可见性有限，漏报风险更高。

技术依赖性

依赖于编程语言和框架；要求与工具兼容。

独立于应用框架，因为它们从外部与应用交互。

SAST 与 DAST 的优缺点

SAST 的优点

  • 在软件开发生命周期的早期识别安全漏洞。
  • 分析代码库，包括基本函数和复杂分支。
  • 直接对源代码进行操作，无需运行应用。
  • 提供实时反馈和全面的洞察，例如漏洞的确切位置。
  • 生成可导出的报告，可使用仪表板进行跟踪。
  • 支持自动化，因此比人工代码评审更快、更高效。

SAST 的缺点

  • 常常产生大量误报。因此，可能需要人工评审。
  • 无法识别运行时或特定于环境的漏洞，例如配置错误。
  • 需要针对每种编程语言使用专门的工具，因此维护较为复杂。
  • 难以理解外部库、API 和 REST 端点。

DAST 的优点

  • 识别仅在应用执行期间出现的漏洞。
  • 从外部运行，无需访问源代码。这对测试第三方应用或已编译代码十分有效。
  • 模拟真实攻击场景，识别 SAST 可能遗漏的风险。
  • 独立于应用的编程语言运行。
  • 评估整个应用和系统，包括内存消耗、资源使用情况和第三方接口。

DAST 的缺点

  • 只关注应用的外层，可能会遗漏更深层次的漏洞。
  • 在软件开发生命周期后期使用，因此修复成本更高、更耗时。
  • 会遗漏 SAST 工具能通过源代码分析识别的某些漏洞。例如，设想一个 Web 应用使用不安全的随机数生成器（如 JavaScript 中的 Math.random()）来创建会话令牌。DAST 可能会遗漏这一缺陷，因为它只测试运行时行为。（但 SAST 可以检测到它。）
  • 对于大型项目，需要定制化的基础设施以及并行运行应用的多个实例，因此资源消耗较大。

何时该使用 SAST，何时该使用 DAST？

SAST 与 DAST 在保障软件开发生命周期安全方面发挥着互补作用。了解何时使用各自的方法，有助于实现全面的安全覆盖。

何时使用 SAST

在开发早期阶段。开发人员使用 SAST 在软件开发生命周期早期识别 SQL 注入和硬编码凭据等漏洞。通过在部署前发现这些问题，他们降低了修复的成本和复杂性。

例如：SAST 工具扫描 Python 代码，标记出源代码中嵌入硬编码 API 密钥的漏洞。开发人员重构代码，改用环境变量来安全地存储和获取密钥。

用于代码评审。SAST 可集成到版本控制系统中，使开发人员能够在提交代码前对其进行扫描。这确保只有安全的代码才会进入代码仓库。

示例：SAST 工具可以检测到这样一种漏洞：文件路径直接由用户输入构造而未经验证，使应用面临路径遍历攻击的风险。开发人员通过清理输入并使用安全的库函数来处理文件路径，从而修复该问题。

在持续集成/持续部署流水线中。SAST 在持续集成/持续交付（CI/CD）过程中运行自动化扫描，为开发人员提供实时反馈。

何时使用 DAST

预生产测试。开发人员使用 DAST 在预发布或 QA 环境中识别运行时漏洞（例如：不安全的配置、身份验证缺陷、访问控制不足）。

示例：DAST 工具可以检测到暴露敏感数据的数据库错误配置。随后开发人员可以在部署前加固该配置。

部署后监控。DAST 工具会持续扫描已部署的应用，查找由环境变化或新出现的威胁所导致的漏洞。这保证应用能够长期保持安全。

测试第三方集成。DAST 可以模拟外部攻击者的视角，识别第三方 API 或互联系统中的漏洞。

例如：DAST 工具测试某个 Web 应用，发现第三方支付 API 中存在一个漏洞：信用卡详细信息通过未加密的 HTTP 连接传输。开发人员通过对所有 API 通信强制使用 HTTPS 来解决该问题。

哪种更有效：SAST 还是 DAST？

SAST 或 DAST 的有效性取决于：

  • 软件开发生命周期的阶段
  • 所要解决的漏洞类型

SAST 在开发早期效果最佳，主要用于识别源代码中的漏洞、降低成本并推广安全编码实践。相比之下，DAST 侧重于预生产或已部署应用中的运行时漏洞，能够深入揭示错误配置和不安全集成等问题。

采用混合方案

与其二选一，不如将 SAST 与 DAST 结合，构建一种多层安全策略，同时应对静态代码和运行时环境中的漏洞。SAST 可以集成到开发早期阶段，在应用编译前发现并修复代码级问题。一旦应用在测试环境中运行起来，DAST 就能识别运行时漏洞，并评估应用在受攻击条件下的行为。

在持续集成/持续交付（CI/CD）流水线中同时自动化 SAST 和 DAST 扫描，可以提供持续反馈，在不牺牲安全性的前提下加快开发进程。

对于敏捷或 DevOps 环境，加入 IAST 或 RASP 等工具可以进一步增强安全性。通过关联 SAST 和 DAST 的结果，组织能够实现更全面、更有效的漏洞管理。

使用 RASP 作为 SAST 和 DAST 的替代方案

运行时应用自我保护（Runtime Application Self-Protection，RASP）是一种直接安装在应用运行所在服务器上的高级安全解决方案。

RASP 将自身嵌入应用的运行时环境。这种集成使 RASP 能够分析应用的逻辑和数据。在分析过程中，它可以：

  • 在异常行为发生时即时检测。
  • 立即阻止恶意活动。

一个关键区别在于，RASP 并不仅仅对潜在问题发出警报——它会主动隔离并化解威胁，无需依赖外部工具，从而阻止攻击。

RASP 为 SAST 和 DAST 提供了一种动态替代方案。SAST 分析静态代码，DAST 模拟外部攻击，而 RASP 则实时运行。它在应用执行期间监控其行为，并通过终止会话或向防御方发出警报来响应实时威胁。

RASP 在保护应用免受那些绕过网络防御或在开发阶段被遗漏的漏洞侵害方面尤其有效。

然而，对 RASP 过度自信可能导致组织忽视安全编码实践。此外，由于 RASP 直接在应用的运行时环境中运行，它可能会影响应用性能。RASP 无法替代修复根本缺陷的必要性，但它能在修复进行期间提供持续的保护。

正如一位 RASP 用户所评论的那样：

「是否使用 RASP 工具，应基于对应用特定需求和风险状况的全面评估。」

未来趋势：结合 SAST、DAST 和 RASP 的应用安全测试

应用测试的未来在于将 SAST、DAST 和 RASP 结合起来，构建全面的安全策略。随着安全挑战日益严峻，将这些工具集成到持续集成/持续交付（CI/CD）流水线中并实现流程自动化，将变得至关重要。

AI 和机器学习的进步将使测试更加高效，因为它有助于减少误报并提升威胁检测能力。

金融与金融服务行业

在金融领域，AI 驱动的工具将改变漏洞检测与缓解的方式。SAST 和 DAST 将继续在开发与预生产阶段识别编码缺陷和运行时问题。

但你不会止步于此：RASP 将借助 AI监控实时交易，更进一步。例如，RASP 可以检测到异常模式（例如：攻击者试图实时利用某个漏洞），并在通知安全团队的同时阻止这些活动。

物联网、边缘计算与互联设备

在物联网领域，这些工具的组合将在保障互联设备安全方面发挥重要作用。具体如下：

  • SAST 可以在开发阶段确认固件不存在漏洞。
  • DAST 可以测试设备间通信协议的安全性。
  • 与此同时，RASP 监控已部署的设备，检测并阻止由新出现的威胁引起的未授权访问尝试或数据泄露。

同样，使用多种方法将有助于物联网生态系统保持韧性。正如我们在众多示例中所阐释的，SAST、DAST 和 RASP 共同预示了这样一个未来：应用的构建与部署将采用更强大、更主动的安全措施。

有韧性的安全始于主动测试

将 SAST、DAST 和 RASP 结合使用，能够提供覆盖整个软件开发生命周期的强大安全性。

通过将这些方法集成到持续集成/持续交付（CI/CD）流水线中并利用 AI 的进步，组织能够主动应对新出现的威胁。这些方法共同提供了一种整体性的方案，保护现代应用免受安全漏洞的侵害。
