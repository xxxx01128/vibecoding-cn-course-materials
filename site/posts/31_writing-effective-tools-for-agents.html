为 AI 智能体编写高效的工具——使用 AI 智能体 \ Anthropic

来源: https://www.anthropic.com/engineering/writing-tools-for-agents

模型上下文协议（Model Context Protocol，MCP）可以为大语言模型（LLM）智能体提供多达数百个工具，用以解决现实世界的任务。那么我们该如何让这些工具发挥最大的效能？

在本文中，我们介绍在各种智能体 AI 系统中提升性能的最有效技巧1。

我们首先介绍你可以如何：

  • 构建并测试工具的原型
  • 与智能体一起创建并运行全面的工具评估
  • 与 Claude Code 等智能体协作，自动提升工具的性能

最后，我们总结出在此过程中发现的、编写高质量工具的关键原则：

  • 选择合适的工具来实现（以及不实现哪些工具）
  • 为工具设置命名空间，以界定清晰的功能边界
  • 从工具向智能体返回有意义的上下文
  • 优化工具响应以提升词元（token）效率
  • 对工具描述和规格说明进行提示工程

构建评估可以让你系统地衡量工具的性能。你可以使用 Claude Code 根据该评估自动优化你的工具。

什么是工具？

在计算领域，给定相同的输入，确定性系统每次都会产生相同的输出；而非确定性系统（如智能体）即便起始条件相同，也可能生成不同的响应。

在传统软件开发中，我们是在确定性系统之间建立一种契约。例如，像 getWeather("NYC") 这样的函数调用，每次被调用时都会以完全相同的方式获取纽约市的天气。

工具是一类新型软件，它体现的是确定性系统与非确定性智能体之间的契约。当用户问"我今天要带伞吗？"时，智能体可能会调用天气工具、依据常识作答，甚至可能先就地点提出一个澄清性问题。有时，智能体可能会出现幻觉，甚至根本无法理解如何使用某个工具。

这意味着在为智能体编写软件时，我们必须从根本上重新思考自己的思路：不能像为其他开发者或系统编写函数和 API 那样来编写工具和 MCP 服务器，而需要针对智能体来设计它们。

我们的目标是扩大智能体能够有效解决各类任务的范围，让它们借助工具去尝试多种成功的策略。幸运的是，根据我们的经验，那些对智能体而言最"好用"的工具，对人类来说往往也出乎意料地直观易懂。

如何编写工具

在本节中，我们将介绍如何与智能体协作，既编写工具，又改进你提供给它们的工具。首先快速搭建工具原型并在本地测试。接着运行一次全面的评估，用来衡量后续的改动。通过与智能体并肩工作，你可以不断重复评估与改进工具的过程，直到你的智能体在现实任务中取得出色的性能。

搭建原型

如果不亲自动手，很难预判哪些工具智能体会觉得好用、哪些不会。先快速搭建一个工具原型。如果你使用 Claude Code 来编写工具（可能是一次性生成），最好向 Claude 提供你的工具所依赖的任何软件库、API 或 SDK（其中可能还包括 MCP SDK）的文档。对大语言模型友好的文档通常可以在官方文档站点上以扁平的 llms.txt 文件形式找到（例如我们的 API 文档）。

将你的工具包装进一个本地 MCP 服务器或桌面扩展（DXT），你就可以在 Claude Code 或 Claude Desktop 应用中连接并测试你的工具。

要将本地 MCP 服务器连接到 Claude Code，请运行 claude mcp add <name> <command> [args...]。

要将本地 MCP 服务器或 DXT 连接到 Claude Desktop 应用，请分别导航至 Settings > Developer 或 Settings > Extensions。

工具也可以直接传入 Anthropic API 调用，以进行编程式测试。

亲自测试这些工具，找出任何粗糙之处。收集用户反馈，帮助你直观地理解你期望工具所支持的用例和提示词。

运行评估

接下来，你需要通过运行评估来衡量 Claude 使用你的工具的效果。首先生成大量立足于真实世界用途的评估任务。我们建议与智能体协作，帮助分析结果并确定如何改进工具。你可以在我们的工具评估指南（cookbook）中端到端地查看这一过程。

生成评估任务

有了早期原型，Claude Code 可以快速探索你的工具，并创建数十组提示词与响应对。提示词应从真实世界的用途中汲取灵感，并基于真实的数据源和服务（例如内部知识库和微服务）。我们建议你避免使用过于简单或表面的"沙盒"环境，因为它们无法以足够的复杂度对你的工具进行压力测试。高质量的评估任务可能需要多次工具调用——甚至多达数十次。

以下是一些高质量任务的示例：

  • 安排下周与 Jane 的会议，讨论我们最新的 Acme Corp 项目。附上我们上次项目规划会议的纪要，并预订一间会议室。
  • 客户 ID 9182 反映，他们因一次购买尝试被收费三次。找出所有相关的日志条目，并确定是否有其他客户也受到同一问题的影响。
  • 客户 Sarah Chen 刚刚提交了取消请求。请准备一份挽留方案。确定：(1) 他们离开的原因，(2) 什么样的挽留方案最有吸引力，以及 (3) 在提出方案之前我们应注意到的任何风险因素。

以下是一些质量较差的任务：

  • 安排下周与 jane@acme.corp 的会议。
  • 在支付日志中搜索 purchase_complete 和 customer_id=9182 。
  • 查找客户 ID 45892 的取消请求。

每个评估提示词都应配有一个可验证的响应或结果。你的验证器可以很简单，只是在标准答案与采样响应之间做精确的字符串比较；也可以很高级，让 Claude 来评判响应。避免使用过于严格的验证器，以免因格式、标点或有效的其他表述方式等无关差异而拒绝正确的响应。

对于每一组提示词-响应对，你还可以选择性地指定你期望智能体在解决任务时调用的工具，以衡量智能体在评估中是否成功理解了每个工具的用途。不过，由于正确解决任务可能存在多条有效路径，请尽量避免过度指定或过度拟合某一种策略。

运行评估

我们建议通过直接调用大语言模型 API，以编程方式运行评估。使用简单的智能体循环（用 while 循环包裹交替进行的大语言模型 API 调用和工具调用）：每个评估任务对应一个循环。每个评估智能体应只得到一个任务提示词和你的工具。

在评估智能体的系统提示词中，我们建议指示智能体不仅输出结构化的响应块（用于验证），还要输出推理块和反馈块。指示智能体在工具调用和响应块之前输出这些内容，可以通过触发思维链（CoT）行为来提升大语言模型的有效智能。

如果你使用 Claude 运行评估，可以开启交错思考功能，即开箱即用地获得类似能力。这将帮助你探究智能体为何调用或不调用某些工具，并凸显出工具描述和规格说明中亟待改进的具体方面。

除了整体准确率，我们建议收集其他指标，例如单次工具调用和任务的总运行时长、工具调用的总次数、词元总消耗量以及工具错误。跟踪工具调用有助于揭示智能体常走的工作流，并为工具的整合提供一些机会。

分析结果

智能体是你得力的伙伴，能帮你发现问题并提供反馈，无论是相互矛盾的工具描述、低效的工具实现，还是令人困惑的工具模式（schema）。不过请记住，智能体在反馈和响应中省略的内容，往往比它们说出来的更重要。大语言模型并不总能如实表达它们的想法。

观察你的智能体在哪些地方卡住或困惑。通读评估智能体的推理和反馈（或思维链），找出粗糙之处。检查原始记录（包括工具调用和工具响应），以发现智能体思维链中没有明确描述的行为。读出字里行间的言外之意；记住，你的评估智能体并不一定知道正确的答案和策略。

分析你的工具调用指标。大量冗余的工具调用可能表明，有必要对分页或词元限制参数进行适当调整；大量因无效参数导致的工具错误可能表明，工具需要更清晰的描述或更好的示例。当我们推出 Claude 的网页搜索工具时，我们发现 Claude 会不必要地在工具的 query 参数后追加 2025，导致搜索结果产生偏差并降低性能（我们通过改进工具描述，引导 Claude 走向正确的方向）。

与智能体协作

你甚至可以让智能体分析你的结果并为你改进工具。只需将评估智能体的记录拼接起来，粘贴到 Claude Code 中。Claude 是分析记录、一次性重构大量工具的专家——例如，确保在进行新改动时，工具的实现和描述保持自洽。

事实上，本文中的大部分建议都来自于使用 Claude Code 反复优化我们的内部工具实现。我们的评估建立在内部工作区之上，映射出内部工作流的复杂性，包括真实的项目、文档和消息。

我们依靠留出测试集来确保不会过度拟合我们的"训练"评估。这些测试集表明，即使在我们用"专家级"工具实现所取得的性能之上，我们仍能获得额外的性能提升——无论这些工具是由我们的研究人员手工编写的，还是由 Claude 自己生成的。

在下一节中，我们将分享从这个过程中学到的一些经验。

编写高效工具的原则

在本节中，我们将所学提炼为几条编写高效工具的指导原则。

为智能体选择合适的工具

工具越多并不总能带来更好的结果。我们观察到的一个常见错误是，工具只是简单地包装现有的软件功能或 API 端点——而不管这些工具是否适合智能体。这是因为智能体与传统软件有着不同的"可供性"（affordances）——也就是说，它们感知自己可以借助这些工具采取哪些潜在行动的方式不同

大语言模型（LLM）智能体的"上下文"有限（也就是说，它们一次能够处理的信息量是有限的），而计算机内存则廉价且充裕。以在通讯录中搜索联系人的任务为例。传统软件程序可以高效地存储并一次处理一个联系人列表，逐一检查后再继续。

然而，如果大语言模型智能体使用一个返回全部联系人的工具，然后不得不逐个词元地通读每个联系人，那就是在把有限的上下文空间浪费在无关信息上（想象一下，自上而下逐页阅读你的通讯录来查找某个联系人——也就是通过暴力搜索）。更好、更自然的做法（对智能体和人类都是如此）是先跳到相关的那一页（或许按字母顺序找到它）。

我们建议构建一些经过深思熟虑、针对特定高影响力工作流的工具，使其与你的评估任务相匹配，并在此基础上逐步扩展。在通讯录的场景中，你可以选择实现 search_contacts 或 message_contact 工具，而不是 list_contacts 工具。

工具可以整合功能，在底层处理多个离散的操作（或 API 调用）。例如，工具可以用相关的元数据丰富工具响应，或在一次工具调用中处理经常串联的多步骤任务。

以下是一些示例：

  • 与其实现 list_users 、 list_events 和 create_event 工具，不如考虑实现一个 schedule_event 工具，它能查找空闲时间并安排日程。
  • 与其实现 read_logs 工具，不如考虑实现一个 search_logs 工具，它只返回相关的日志行及部分上下文。
  • 与其实现 get_customer_by_id 、 list_transactions 和 list_notes 工具，不如实现一个 get_customer_context 工具，它一次性汇总某位客户近期及相关的所有信息。

确保你构建的每一个工具都有清晰、独特的用途。工具应使智能体能够像人类一样细分并解决任务——前提是能访问相同的底层资源——同时减少那些本会被中间输出所占用的上下文。

工具过多或工具之间功能重叠，也会分散智能体的注意力，使其无法采用高效的策略。谨慎、有选择地规划你要构建（或不构建）哪些工具，会带来实实在在的回报。

为工具设置命名空间

你的 AI 智能体可能会获得数十个 MCP 服务器和数百个不同工具的访问权限——包括其他开发者提供的工具。当工具在功能上重叠或用途模糊时，智能体可能会困惑于该使用哪一个。

命名空间（将相关工具归入共同的前缀之下）有助于界定大量工具之间的边界；MCP 客户端有时默认就会这样做。例如，按服务（如 asana_search、jira_search）和按资源（如 asana_projects_search、asana_users_search）为工具设置命名空间，可以帮助智能体在合适的时候选择合适的工具。

我们发现，在基于前缀和基于后缀的命名空间之间做选择，会对我们的工具调用评估产生不小的影响。影响因大语言模型而异，我们建议你根据自己的评估来选择合适的命名方案。

智能体可能会调用错误的工具、用错误的参数调用正确的工具、调用的工具太少，或者错误处理工具响应。通过有选择地实现那些名称能反映任务自然划分的工具，你既减少了加载到智能体上下文中的工具数量和工具描述，又把智能体计算从智能体的上下文转移回工具调用本身。这降低了智能体整体犯错的风险。

从工具返回有意义的上下文

同样地，工具实现应注意只向智能体返回高价值的信息。它们应优先考虑上下文相关性而非灵活性，并避免使用底层技术标识符（例如：uuid、256px_image_url、mime_type）。像 name、image_url 和 file_type 这样的字段，更有可能直接为智能体的后续行动和响应提供有用信息。

与晦涩的标识符相比，智能体在处理自然语言名称、术语或标识符时往往成功得多。我们发现，仅仅将任意的字母数字 UUID 解析为语义上更有意义、更易理解的语言（甚至采用从 0 开始的 ID 编号方案），就能通过减少幻觉显著提升 Claude 在检索任务中的准确率。

在某些情况下，智能体可能需要灵活地同时处理自然语言输出和技术标识符输出，哪怕只是为了触发后续的工具调用（例如 search_user(name='jane') → send_message(id=12345)）。你可以通过在工具中暴露一个简单的 response_format 枚举参数来同时支持两者，让智能体自行控制工具返回 "concise"（简洁）还是 "detailed"（详细）的响应（见下图）。

你可以添加更多格式以获得更大的灵活性，类似于 GraphQL，你可以精确选择想要接收哪些信息。以下是一个用于控制工具响应详细程度的 ResponseFormat 枚举示例：


enum ResponseFormat {
   DETAILED = "detailed",
   CONCISE = "concise"

优化工具响应以提升词元效率

优化上下文的质量固然重要，但优化工具响应中返回给智能体的上下文数量同样重要。

对于任何可能耗尽大量上下文的工具响应，我们建议结合使用分页、范围选择、过滤和/或截断，并为其设置合理的默认参数值。对于 Claude Code，我们默认将工具响应限制在 25,000 个词元以内。我们预计智能体的有效上下文长度会随时间增长，但对上下文高效型工具的需求将始终存在。

如果你选择截断响应，务必用有用的指令来引导智能体。你可以直接鼓励智能体采用更节省词元的策略，例如在知识检索任务中进行多次小规模、有针对性的搜索，而不是一次宽泛的搜索。类似地，如果工具调用引发错误（例如在输入验证期间），你可以对错误响应进行提示工程，使其清楚地传达具体且可操作的改进建议，而不是晦涩难懂的错误代码或回溯信息。

对工具描述进行提示工程

现在我们来看改进工具最有效的方法之一：对你的工具描述和规格说明进行提示工程。由于这些内容会被加载到智能体的上下文中，它们能够共同引导智能体采取有效的工具调用行为。

在编写工具描述和规格说明时，想一想你会如何向团队里的新同事介绍这个工具。把你可能默认具备的上下文——专用查询格式、小众术语的定义、底层资源之间的关系——都考虑进来，并明确写出来。通过清晰描述预期输入和输出（并用严格的数据模型加以约束）来避免歧义。尤其要注意，输入参数的命名必须无歧义：与其使用名为 user 的参数，不如使用名为 user_id 的参数。

有了评估，你就能更有把握地衡量提示工程的效果。即便是对工具描述做细微的改进，也可能带来显著的提升。在我们对工具描述进行了精确的改进之后，Claude Sonnet 3.5 在 SWE-bench Verified 评估中取得了当时最先进的性能，错误率大幅降低，任务完成率显著提升。

你可以在我们的开发者指南中找到有关工具定义的其他最佳实践。如果你在为 Claude 构建工具，我们还建议阅读有关工具如何动态加载到 Claude 的系统提示词中的内容。最后，如果你在为 MCP 服务器编写工具，工具注解有助于披露哪些工具需要开放世界访问权限或会进行破坏性更改。

展望

要为智能体构建高效的工具，我们需要将软件开发实践从可预测的确定性模式重新调整为非确定性模式。

通过本文描述的这种迭代式、评估驱动的过程，我们总结出了工具之所以成功的一致规律：高效的工具有意识地被清晰定义，审慎地使用智能体上下文，能够在各种工作流中组合使用，并使智能体能够直观地解决现实世界的任务。

在未来，我们预计智能体与世界交互的具体机制会不断演进——从 MCP 协议的更新，到底层大语言模型本身的升级。借助系统化、评估驱动的方法来改进智能体工具，我们可以确保随着智能体变得越来越强大，它们所使用的工具也会随之演进。
