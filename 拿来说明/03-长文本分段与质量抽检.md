# 拿来说明 03：长文本分段与质量抽检

> 关键决策：**按语义标题切长文 + 用机器指标反向校验漏译**。解决"AI 翻长文后半段悄悄缩水"的隐性问题。
> 结构：背景 → 原文/素材 → prompt → 产出 → 对比 → 复用方法。

---

## 一、要解决的问题

这套讲义里有 5 篇超长文（`agentic-ai-threats` 5.5 万字符、`context-rot` 5.1 万、3 篇 PDF 各 5–7.5 万字符）。AI 处理长文时有两类典型失效：

1. **上下文衰减**：输入过长时后半段翻译质量下降，甚至整章被"概括"掉；
2. **隐性漏译**：输出看起来完整，实则某几段被跳过——人工不逐段对照极难发现。

Rubric 明确把"大段漏译"列为扣分项。所以要同时解决"怎么切"和"怎么验"。

## 二、原文 / 素材（输入）

以 `原文/07_context-rot.md`（5.1 万字符、8 个标题段）为例：

> **原文片段**（标题结构）：
> `# Context Rot ... ## Why does context rot happen? ## The "needle in a haystack" problem ... ## How to mitigate context rot ...`

若整篇一次性交给 AI，后 2–3 个小节最容易被压缩或遗漏。

## 三、Prompt（我用 AI 做的事）

**Prompt A — 分段策略**

> 写一个按标题边界切分长文的脚本：超过 6000 字符的文件，在 `#`/`##` 标题处切块，保持每段语义完整；把过小的尾段合并；支持 --dry-run 先统计不落盘。不要按字符硬切，避免把一句话劈成两半。

**Prompt B — 抽检脚本**

> 写一个翻译质量抽检脚本，逐篇对比原文与译文，输出：① 覆盖率（有正文讲义中有译文的比例，目标≥80%）；② 竞争译法计数；③ 标题数比值、代码块数比值（结构保真）；④ 译文/原文字符比，低于 0.35 判为疑似漏译。输出人读 Markdown 与机读 JSON。

## 五、对比

| 维度 | 整篇硬翻、人工目测 | 分段 + 机器抽检（本方案） |
|---|---|---|
| 长文后半段 | 易缩水、整章丢失 | 切成 8 段逐段翻，无衰减 |
| 漏译发现 | 靠人工逐字对照，几乎不可行 | 字符比 + 标题数比值自动报警 |
| 术语漂移 | 长文中后段易变调 | 每段都注入术语表，QA 再扫描 |
| 结构保真 | 代码块可能被译坏 | 代码块数比值校验，原样保留 |
| 复核成本 | 不可复核（凭印象） | `qa_report.json` 机器生成，谁都能重跑 |
| 阈值设计 | 无 | 0.35（漏译）/ 0.6（标题）/ 0.7（代码块），中文场景已放宽 |

**一个真实的阈值权衡**：最初想用 0.5 作漏译线，但中文比英文紧凑，正常全文翻译的比值常在 0.5–0.7，0.5 会大量误报；改为 0.35 后误报消失，仍能抓住真正的摘要式漏译（比值<0.3）。

## 六、怎么拿来用

1. 设 `config/course.json` 的 `chunking.max_chars`（默认 6000，按你的模型上下文调整）。
2. 跑 `python pipeline/02_segment.py`，先看 dry-run 统计，确认切分粒度合理。
3. 对 `data/segments/` 中的片段逐段翻译（可并行），拼回同名译文文件。
4. 跑 `python pipeline/03_qa_check.py`，重点看 `ratio` 与"标题/代码块"比值两列。
5. 把 `status=fail/warn` 的条目列入人工复核清单。

> **一句话**：AI 翻长文不可怕，可怕的是"看起来翻完了"；用语义切分保证不衰减，用机器指标保证不漏——**让隐形错误显性化**，这才是质量控制的本质。
