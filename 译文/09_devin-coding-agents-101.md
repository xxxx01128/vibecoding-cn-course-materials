# 编码智能体 101：真正把事情做成的艺术

现在是 2025 年。编码智能体并非魔法，但它们大概是我们手边最接近魔法的东西了。我们注意到，一些工程师——尤其是资深（senior）到首席（staff）级别的工程师——比其他更快取得了成功。在这里，我们分享一些最重要的经验教训，它们来自我们客户和我们自己的实践。

关于本指南：

## 与产品无关

我们讨论的是那些能帮助你使用任意编码智能体取得成功的技巧。

## 务实

我们奉上自己最中意的一些可落地建议。

## 技术向

尽管编码智能体对许多人都很有价值，但本指南是专为工程师而写的。

开发者工具一直在快速演进。十年前，它是自动补全和智能感知（intellisense），能够提示方法名并执行程序化重构。四年前，它是 copilot 和 Tab 补全，能帮你写出接下来的几行代码。两年前，它是生成式聊天机器人，能够辅助你的开发并为你生成整个文件。而今天，它是自主智能体，能够在几乎无需人工干预的情况下，从最初的描述一路做到最终的拉取请求（PR）。过去两年里，我们一直专注于通过打造 Devin 来实现这一愿景。如今，人们对自主智能体的兴趣正达到新的高度，尤其是近期又发布了多款类似产品[1]除 Devin 之外，近期发布的产品还包括 OpenAI 的 Codex 和 Google 的 Jules。一些本地智能体如 Cursor 和 Claude Code，也可以在并行工作区中运行，以复现类似的效果。。这些智能体可以以多种形式出现，包括 Web 应用、移动应用，以及与 Slack、GitHub、Linear 和 Jira 等热门工具的集成。

虽然人类与 AI 助手搭档所能取得的成就，胜过任何单独的 AI，但自主智能体端到端处理任务的能力，让多任务处理达到了一个新的层次，把每一位工程师都变成了工程经理。

适应与这些新 AI 同事高效协作可能需要一些时间。有趣的是，我们观察到资深到首席级别的工程师往往最快采用并熟练使用这些工具。最终，这些工具将在所有级别的工程团队中变得司空见惯。基于我们的经验和客户反馈，我们希望分享一些关键洞见和经验教训，帮助大家成功地将这些工具融入自己的工作流程。

## 提示词基础

这些基本准则将帮助你在 2025 年有效地与编码智能体交互。如果你只能记住一件事，那至少记住这些。

### 说明你希望事情怎么做，而不只是做什么

把智能体想象成一位决策可能不太可靠的初级编程搭档。简单的任务可以直接描述，但对于更复杂的任务，要一开始就清楚勾勒出你偏好的方法。提前向智能体提供整体架构和逻辑，不仅能提高它成功的概率，还能减少你评审代码的时间，因为你本来就已经熟悉预期的方法。

#### 示例：

不要只说「添加单元测试」，而要指明要测试的功能，找出重要的边界情况，并说清楚哪些地方需要 mock（如果有的话）。

### 告诉智能体从哪里入手

想一想，如果由你自己来处理这个任务，你会从哪里开始。即便你不知道具体的文件名或函数名，也要提到代码仓库、相关文档以及涉及的关键组件。清楚地指出这些要素，能最大限度减少无效劳动和困惑。

#### 示例：

「请在我们的代码中添加对 Google 模型的支持。你应该查看[这里](link)的最新文档，并在 model groups 目录中新建一个实现文件」

### 践行防御式提示

想象一下，把同样的提示词交给一位新来的实习生。困惑或错误最可能出现在哪里？预先想到这些点，并主动澄清你的指令，以避免歧义。

#### 示例：

「请修复我们搜索模块的 C++ 绑定，使其通过新的单元测试。注意，每次改动代码后，你很可能都需要重新编译绑定，然后再进行测试。」

### 让智能体能访问 CI、测试、类型和 linter

智能体的很多「魔力」来自它们自我纠错、并依据错误信息不断迭代的能力。通过类型检查器、linter 和单元测试等工具提供强有力的反馈闭环，能大幅提升它们的表现。可以考虑用带类型的 Python 而非普通 Python，或用 TypeScript 而非 JavaScript。教你的智能体如何运行常见的检查和测试，确保它拥有所有必要的依赖包和访问权限。如果智能体可以与浏览器交互，就为如何运行你的前端开发环境提供清晰的说明。

#### 示例：

我们团队从以无类型的 Python SDK 为主，全面转向了带类型的 SDK（这其实也是一项非常适合交给编码智能体完成的任务）。

### 发挥你的专业特长

当你熟悉自己的代码库时，上面的一切都会变得更容易。即便是简单的任务，也会因你验证逻辑和结果的能力而受益。人工监督依然必不可少——归根结底，代码的最终正确性由你负责。即便这些工具变得愈发精密，责任归属与验证仍将是人类工程师的关键职责。

## 在工作流程中使用智能体

一旦你掌握了与智能体对话的基本功，就该把这些 AI 助手纳入你的日常工作流程了。下面有一些实用的方法，能让智能体成为你常规工作的一部分：

### 立即承接新任务

想象一位同事给你发消息：「嘿，我们能快点做个 X 吗？」或者「我们需要调整一下 Y。」不要让这些打断你的心流，只需给自主智能体发一条简短的提示词，让它去调查或做出改动。这样你就能专注于自己的主要任务。有个有趣的副业项目点子？需要快速做个原型、抓取数据，或复现某项研究？交给你的智能体，稍后再回头看。

#### 示例：

许多团队在讨论 bug 修复或小的功能更新时，只需在 Slack 上 @Devin 即可。

### 随时随地写代码

想象一下，你正在通勤或旅途中，突然冒出一个紧急 bug，或者你意识到自己可能在代码里留了个错误。别担心！自主智能体通常支持移动端访问，让你能立即处理这些问题。无论是通过 Slack 的移动应用，还是专门的移动 App，许多智能体都能让你随时随地解决问题，哪怕你的 wifi 信号很不稳定。

#### 示例：

拥有这种灵活性，让我们自己的团队在乘车和坐飞机时效率提高了不少。

### 把杂活交出去

还在为二分查找旧提交、或为新功能更新文档而头疼？把这些重复性任务交给你的智能体吧。你会节省宝贵的时间，把精力集中在更有创造性、更有影响力的工作上。

#### 示例：

在我们团队，工程师交付一个改动后，再让智能体更新所有相关文档和面向用户的文案，是很常见的做法。

### 摆脱分析瘫痪

纠结于一次重构是否真能简化你的代码？在两种架构方案之间难以取舍？那就让你的智能体把两种方案都实现出来。有了具体的例子可供比较，决策就变得简单直接，而舍弃其中一个方案也不会伤害任何人的感情。

#### 示例：

在 Lexical 和 Slate 之间为文本框做选择时，我们让智能体分别实现了两者。Slate 凭借更佳的最终效果胜出。

### 搭建预览部署

将你的持续集成/持续交付（CI/CD）流水线设置为在每个新 PR 时自动创建预览部署，为你提供一个即时可访问的线上 URL。在评审由 AI 智能体完成的前端任务时，这一点尤其方便。

#### 示例：

Vercel 是一个部署平台，让预览部署变得极其简单。

## 委派更大的工单

当你的拉取请求（PR）的规模和复杂度超出区区几个文件时，想一次性处理完它们就变得很有挑战性。然而，真正掌握如何委派中大型任务（通常是 1 到 6 小时的工作量），才是自主智能体投资回报率（ROI）最高的地方。你节省的将不只是几分钟，而是数小时的生产力。小任务或许能轻松完成，但把智能体的能力延伸去处理更大的任务，才会带来最大的回报。

### 自动化你的初稿

对于规模较大的任务，用自主智能体为你的 PR 创建初稿，可以迅速启动进展，并大幅减少你的工作量。这方面的成功取决于你能否提前清楚地传达你想要的方法。把自己想象成指导初级开发者的架构师。清晰、详细的指令有助于避免把不必要的时间花在纠正智能体代码中的根本性误解上。

领域起草打磨

新闻业记者收集初步信息，撰写文章初稿编辑评审草稿、核实事实、润色，并最终定稿付印。

餐饮业流水线厨师准备食材并制作初步菜品。副厨师长添加调味料并调整菜品使其更美味，之后再端给食客。

编程自主智能体根据初步计划开始处理任务，并创建首版解决方案人类开发者评审 PR 草稿，给出反馈，并在合并前进行人工打磨

🛑 请记住，大型任务（目前）还做不到完全无人值守。对于更具挑战性的任务，要预期会有多轮反馈循环，并预留一些人工打磨的时间。一个现实的目标是节省约 80% 的时间，而非完全自动化；你的专业判断对于验证和最终的质量保证仍然至关重要。

### 共同制定产品需求文档（PRD）

对于那些复杂或定义模糊的任务，与你的自主智能体协作制定一份详细计划，可能非常有效。即便你一开始并不清楚每个细节或需求，这也完全没问题。可以先让你的智能体去探索一些发现性问题，比如「我们的认证系统是如何工作的？」或「哪些服务可能会受到影响？」你也可以让智能体找出具体的相关代码目标，供你尽早确认。

某些智能体，如 Devin 和 Claude Code，提供专门的规划模式，专注于阅读和探索现有代码，而非立即修改它。如果你希望在委派任务前做更深入的准备，像 [deepwiki.com](http://deepwiki.com) 和 Devin Search 这样的专业代码库搜索工具，能快速提供对你代码库的洞见，帮助简化流程。

### 设置检查点

对于由多个部分组成的任务，尤其是那些涉及多个代码库的任务，要沿途设立清晰的检查点：

规划 → 实现一个分块 → 测试 → 修复 → 检查点评审 → 下一个分块

明确要求在每个重要阶段之后暂停，尤其是那些跨越多个层级（例如数据库、后端、前端）构建的复杂功能。利用这些检查点确保实现符合你的预期，澄清疑惑（例如「解释一下认证流程并确认其安全性」），并及早纠正方向，避免问题层层蔓延。

#### 示例：

「我希望你实现这个功能，它将跨越我们的数据库、后端和多个前端界面。请先规划出所需的数据库 schema 变更，完成后告诉我，以便我执行迁移。」-> 「现在请实现后端的改动，并添加测试以确保 XYZ 正常工作。完成后告诉我」-> 「现在在我们的 Web 和移动界面中都实现相应改动，以调用新的后端接口」

### 教它验证自己的工作

在给出反馈时，不要只是指出问题（「这个函数不工作」）。要清楚地说明你的测试流程，使智能体能够独立验证以后的任务。对于那些你会反复使用的测试模式，把它们整合进智能体的永久知识库中（参见「添加到你的智能体知识库」）。

#### 示例：

在 Devin 中，我们主动提示用户把重要的测试流程保存到智能体的持续记忆中，从而简化未来的交互。

### 提高 AI 热点区域的测试覆盖率

目前，智能体还无法完全做到交互式地彻底测试所有场景。在被 AI 大幅修改的区域提高测试覆盖率，能让你对智能体的输出更有信心。扎实的测试意味着，那些看起来正确的代码可以放心合并，无需担忧。

#### 示例：

在把实现工作交由我们的 AI 从 Python 转写为 C 之前，我们团队先加强了代码库关键部分的单元测试。

## 自动化工作流

智能体对传入事件的响应速度远快于人类，而且与人类同事相比，它们乐意得多去做枯燥、重复的工作。

### 为你最重复的工作创建快捷方式

工程团队经常遇到重复性的日常任务。这些任务非常适合用智能体来实现自动化。常见的例子包括：

- 移除功能开关（feature flag）
- 依赖升级
- 在新功能的 PR 上修复问题并补充测试

要高效地做到这一点，经验丰富的工程师通常会创建一个健壮、可复用的提示词模板[2]在 Devin 中，这些被称为 playbook，以便在这些场景下反复运行。

#### 示例：

我们的一位客户每当开发新功能时，就会自动触发三个专门用于编写单元测试的智能体。

### 智能代码评审与规范执行

虽然存在一些用于快速代码评审的专用工具[3]例如 Greptile 和 CodeRabbit，但自主智能体也不失为一个有趣的选择，能给出更准确的洞见，尤其是当它们已经索引了你代码仓库的功能时。

#### 示例：

在 Cognition，我们喜欢维护一份工程师最常犯错误的清单，并把这份清单提交到代码库中。然后，与其编写传统的 lint 规则来捕捉这些错误（这通常做不到），我们改为让一个智能体在每个新 PR 上运行，检查这些错误。

### 接入故障事件与告警

你还可以设置自主智能体，使其在响应特定事件时自动触发。例如，Devin 提供了易于使用的 API，其他智能体则可以通过命令行界面（CLI）命令集成到自定义工作流中。这些配置与模型上下文协议（MCP）配合使用时效果尤其好，可用于摄入第三方错误日志。

⚠️ 在排查和分类生产服务中的问题方面，AI 的调试能力并不出色。与其让 AI 在 bug 出现时端到端地修复它们，更实际的做法往往是让 AI 只标记出最可疑的错误、改动等。

## 自定义与提升性能

### 环境配置

没有什么比一个不完整或不匹配的环境更能拖慢智能体了。为了让一切顺利运行，要让智能体的环境与团队的环境完全一致。这包括语言版本、依赖包和自动化检查。例如，应该在智能体的环境中安装 pre-commit，并使用 .envrc 之类的工具或 .bashrc 的自定义配置，自动加载环境配置（密钥、语言版本、虚拟环境、浏览器登录状态）。

#### 示例：

我们为智能体的浏览器预先配置好登录状态，省去了手动认证的麻烦，让测试变得容易得多。

### 构建自定义命令行工具与 MCP

MCP 随处可见，而且能快速搭建并试验将你的智能体连接到外部工具[4]在 Devin 中，MCP 仍处于 beta 阶段，我们正在探索支持它们的最佳方式。请联系我们以获取访问权限！。但很多人忽略了为智能体设置简单的 CLI 脚本。举个简单的例子，你可以给智能体一个脚本，让它根据工单 ID 拉取某个 Linear 工单的信息。你或许还想给智能体一个工具，可靠地执行工作流中的常见环节，比如一个用于重启本地开发环境的脚本。

#### 示例：

我们有一位客户，他们创建了一个 CLI 工具，只显示测试套件中第一个失败的测试，并因此大获成功。这个 CLI 会提示智能体只专注于那个测试，并附带详细的错误信息，从而让智能体在长任务中获得更高的成功率和更快的完成速度。

### 添加到你的智能体知识库

如果你的智能体犯了一些常见的错误，这正是把你的反馈固化到智能体知识库中的好时机。在 Devin 中，有一套专门的知识管理系统。许多产品提供 .rules 文件、.md 文件，供智能体永久摄取。不要只给它关于你所用框架的准则，还要告诉它项目的整体架构。告诉它对于不同类型的任务，通常采用哪种测试方式，如何运行重要命令，以及你推荐使用哪些工具。

#### 示例：

我们会给智能体提供关于添加新服务路由时应遵循的特定流程的知识。这些信息包括它需要在前端和后端添加样板代码的所有位置。结果，这些任务如今都可以轻松委派给我们的 AI。

## 自主智能体的局限性

### 调试能力有限

bug 报告可能看似简单，实则不然。但许多 bug 往往不仅需要具备访问数据库和日志的权限，还需要超出当今大多数 AI 智能体能力的调试水平。如果用 AI 辅助调试，我们建议让它给出一份可能的根本原因清单，而不是试图自行调试并修复一切。然后，人类可以根据自己的经验判断哪一个是真正的根本原因。但一旦原因确定，智能体在实现修复方面依然能派上很大用场。

### 细粒度视觉推理能力差

一般来说，当今的模型在细节层面的视觉推理能力并不强，达不到匹配设计截图或 Figma 原型所需的程度。对于那些可以用代码层面来描述的视觉内容（例如把 Figma 中的代码给它），它们最为可靠。如果你希望它匹配你的视觉风格，就应该使用一套带有可复用组件的良好设计系统。

### 知识截止

每当你想使用一个新的库时，都应该明确地把它指向最新的文档。否则，由于预训练基础模型的知识截止，大多数智能体会沿用这些库的旧模式。如果你把它指向文档，一个好的智能体能够克服这一点，但你必须对此保持警惕（记住，智能体甚至不知道这些库还有新版本）。

## 管理时间并减少损失

并非每次使用智能体都能成功。在 2025 年，这些智能体的结果确实存在很大差异。工作的一部分，就是学会如何以这样一种方式使用智能体：最大化遇到成功结果的概率，同时最小化浪费的时间和词元（token）。

### 愿意及早止损

刚接触智能体的人常犯的一个错误是，即便智能体的工作已经偏离轨道，他们仍执着于让这次交互成功。如果你发现自己在想「它在无视我的指令」或「这东西在原地打转」，那就应该果断终止这次对话，或者手动接管。继续发更多消息，更可能说明你的任务本身固有的复杂度超出了智能体的能力，而不是某个可以纠正的小错误。

### 让尝试多样化

如果你刚接触智能体，我们建议一开始分散下注。尝试一系列不同的提示词和思路。在你看到智能体天然擅长的任务类型上加码——而在它们不擅长的任务上及时止损。不必强求你的智能体每次都取得成功。

### 没有进展时重新开始

与人类相比，对智能体而言，重新开始是正确得多的答案。如果你给了一个智能体任务，而它难以回应反馈或纠正方向，那么换一个新的智能体、把所有指令一次性给全、从头开始，往往能快得多地取得成功。智能体纠正一团糟的环境的能力，远逊于它从零写出全新代码的能力。

## 安全与权限

### 为你的智能体创建账户

用一个临时邮箱有助于安全地测试网站。如果智能体需要访问云资源，就为它创建自定义的 IAM 角色。

### 给它一个开发／预发布环境

理想情况下，智能体使用的测试配置应与你团队中的工程师一致。我们建议完全避免授予其对生产服务的访问权限。在使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。

### 只读 API 密钥

在可能的情况下，给它只读权限。我们发现，让人类手动运行任何与外部服务交互的脚本，仍然是有益的。

## 重大变革将至

我们坚信，软件工程师不会消失。即便编码智能体变得更聪明、更强大，深厚的技术专长和对代码库的透彻了解依然弥足珍贵。对你的项目、系统和代码拥有真正的掌控权，如今比以往任何时候都更加关键。在我们团队今天，工程师被期望在监管多个系统的同时，依然保持深入的理解和深思熟虑的判断力。随着自动化放大你的影响力，同时处理并行任务的能力将不只是成为可能；它将变得必不可少。我们很高兴分享在为自身组织应对这一转变做准备时所积累的洞见，希望你和你的团队也能在不断演进的软件开发世界中蓬勃发展。
