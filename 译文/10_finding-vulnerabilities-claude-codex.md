# 使用 Claude Code 和 OpenAI Codex 发现现代 Web 应用中的漏洞 | Semgrep

> 来源: https://semgrep.dev/blog/2025/finding-vulnerabilities-in-modern-web-apps-using-claude-code-and-openai-codex/

TL;DR：我们评估了 AI 编码智能体在真实代码中发现漏洞的有效性。

- 如何开展：我们让 Anthropic 的 Claude Code（v1.0.32，Sonnet 4）和 OpenAI 的 Codex（v0.2.0，o4-mini）在 11 个流行且大型的开源 Python Web 应用中寻找漏洞。两者合计产出超过 400 条安全发现，由我们的安全研究团队逐条复核。
- AI 编码智能体确实能发现真实漏洞：Claude Code 发现了 46 个漏洞（真阳性率 14%——TPR，假阳性率 86%——FPR），Codex 报告了 21 个漏洞（真阳性率 18%，假阳性率 82%）。其中约 20 个属于高危漏洞。
- AI 擅长理解上下文，却在数据流追踪上卡壳：Claude Code 最擅长发现不安全的直接对象引用（IDOR）漏洞，真阳性率达 22%（59 条报告中 13 条正确），但在跨多个文件和函数做污点追踪时表现吃力，SQL 注入的真阳性率仅 5%（2/38），XSS 仅 16%（12/74）。OpenAI Codex 几乎报不出任何正确的 IDOR（真阳性率 0%（0/5）），在 SQL 注入（0%（0/5））和 XSS（0%（0/28））上表现极差，却出人意料地比 Claude Code 报告了更多正确的路径遍历问题，真阳性率 47%（8/17）。
- 非确定性是一大难题：在完全相同的代码库上多次运行完全相同的提示词，往往产生截然不同的结果。在一个应用中，三次相同的运行分别产出了 3 条、6 条和 11 条不同的发现。

关键要点：

- 使用相对简单、以安全为重点的提示词，AI 编码智能体就已经能在真实应用中发现真实漏洞。
- 但要注意：结果可能相当嘈杂（假阳性率高），这取决于漏洞类别，在 SQL 注入、XSS 和 SSRF 这类传统注入式漏洞上尤其如此。
- 细致的评估和基准测试，是理解某种方法发现漏洞 effectiveness（有效性）的关键（这一点一直如此，面对大语言模型（LLM）这类非确定性工具时更甚），也是判断你的改进是否走在正确方向上的关键。

## 引言

在 Semgrep，我们全身心投入应用安全（AppSec）。长期以来，我们一直在产品中把 AI 投入生产（[Assistant 背后的技术](https://semgrep.dev/blog/2024/the-tech-behind-semgrep-assistant/)、[用 promptfoo 测试我们的 AI 工作流](https://semgrep.dev/blog/2024/does-your-llm-thing-work-how-we-use-promptfoo/)、[用安全研究员的分诊来评估自动分诊的表现](https://semgrep.dev/blog/2025/building-an-appsec-ai-that-security-researchers-agree-with-96-of-the-time/)），持续研究传统确定性分析与现代 AI 的上下文能力的最佳组合，而不盲目追逐潮流。

这项研究是这一持续使命的一部分。我们正展开一场深入、公开的探索，来回答一个人人都在关心的问题：大语言模型在源代码中发现漏洞，究竟有多有效？

## 关于基于 AI 的漏洞挖掘的开放性研究问题

为了指引我们的调查，我们把「大语言模型擅长发现 bug 吗？」这个宽泛的问题，拆解成更具体、可衡量的问题。

- 基于大语言模型的漏洞发现，假阳性率和假阴性率是多少？它会随编程语言、框架、代码库规模或漏洞类别而变化吗？对代码的写法有多敏感？
- 造成假阳性和假阴性的常见原因是什么？
- 分析的确定性有多高？你每次都能得到相同的结果吗？

针对注入类漏洞，我们想知道：

- 大语言模型在追踪用户输入从 source（例如用户提供的值）到 sink（例如消费原始 SQL 查询的方法）之间的流动时，有多有效？
- 它能跨函数和跨文件追踪数据吗？
- 它能对净化函数及其他安全控制措施进行推理吗？
- 它能对来自第三方开源依赖的函数进行推理吗？

## 常见 SAST 基准测试的问题：缺乏真实性

在深入我们的发现之前，先谈谈我们如何衡量 AI 的表现。目前许多研究和论断所依赖的基准测试虽然有价值，却无法完整捕捉真实世界代码的复杂性。

- 含有已知漏洞的应用：这些基准测试只使用带有已知漏洞的开源应用；多亏了 Kinnaird McQuade，许多这样的应用都能在 vulnerable-apps 中找到。如果你读这个博客，可能会认出其中一些名字：WebGoat、JuiceShop、OWASP Benchmark 等等。但这些应用有个问题：当前的大语言模型很可能已经把这些数据仓库的代码，以及互联网上大量公开的 Write-up 都摄入了训练集，这让它们拥有先备知识，从而扭曲了结果。它们的代码往往也不够真实，充斥着大量注释、标注和变量名，直接或间接地暗示漏洞在代码中的位置或利用方式。有时，工具的结果甚至直接被提交进了仓库——比如 javaspringvulny 的 SearchService.java、juiceshop 的文件，挑战线索就写在文件名里……
- XBOW 为自动化渗透测试工具提供了基准测试，但它并不适配静态分析：其代码往往过于刻意、过于简单，无法代表真实应用。ZeroPath 在净化这些代码上做得不错，但只有一小部分被净化了。而且，这些测试用例每一个都是微型应用，专门用来模拟某种特定的攻击场景。如果只看 Python 基准测试，XBOW 有 45 个；45 个不同的微型应用，平均代码行数不到 98 行、只有 3 个 Python 文件。这规模太小，无法体现跨整个代码库或跨多个函数进行搜索与推理的复杂性。
- CVE 记忆偏差：由于大语言模型是在来自互联网的巨量公开数据语料上训练的，其中就包括那些发现并修复过 CVE 的代码库本身。这造成了一个根本性的数据污染问题。AI 可能并不是通过新颖的分析检测出漏洞，而只是认出了它在训练时记住的一种模式。

最近，学术界设计出了一些基准测试，例如 [CyberGym](https://www.cybergym.io/)、[Eyeballvul](https://tchauvin.com/eyeballvul-paper) 或 [SecVulEval](https://huggingface.co/datasets/arag0rn/SecVulEval)。这些是很大的进步，也更接近真实世界的例子，但它们没有聚焦于现代 Web 应用，或者把漏洞从更大的应用上下文中割裂了出来。

- EyeballVul：这是 Timothée Chauvin 提出的一个较新的基准测试，它从开源项目中提取真实、经人工审核的漏洞，并以最小化、可复现的测试用例形式呈现。虽然基于真实代码，它仍然把漏洞从更大的应用上下文中隔离出来，让搜索问题变得更容易。
- SecVulEval 和 CyberGym：这两套基准测试旨在评估 C 或 C++ 中的漏洞。虽然在其领域内很有价值，但聚焦于 C 和 C++ 意味着这些数据不适用于主导现代云原生开发的 Python/JavaScript 及其他以 Web 为中心的语言。

尽管上述每种方法都有用，也都应当适时使用，但它们未必反映现代软件开发的现实。真实世界的应用并不是干净、隔离的函数。它们是依赖、框架和业务逻辑交织而成的复杂网络。

我们的方法不同。我们在 11 个大型的、基于 Python 的、活跃维护的开源项目上进行测试，这些项目使用常见的 Web 框架（Django、Flask、FastAPI）编写。我们的方法与先前的方法互补，而且我们认为它独一无二，因为：a）力求代表真实世界中 AI 驱动的漏洞发现（而非小型、隔离的合成样例）；b）不受模型训练数据污染；c）代表大多数开发者和公司实际在构建的应用类型——使用现代语言和框架的 Web 应用。

### 我们的发现

- Claude Code 和 Codex 如今都很有用：它们能发现真实的安全漏洞，但噪音非常大。整体噪音仍然很高，但它们确实在这些流行的开源 Python Web 应用中发现了真实的安全漏洞。总体而言，Claude Code 发现了 46 个漏洞（真阳性率 14%，假阳性率 86%），Codex 报告了 21 个漏洞（真阳性率 18%，假阳性率 82%）。
- 许多 IDOR bug 初看之下像是真的，Claude Code 还给出了可信的修复建议：大语言模型不仅能发现这些 bug，还能提出可信的修复方案，例如依据代码中已有的模式注入新的权限检查。IDOR 问题很难分诊，我们不得不对其中大多数进行测试才能确定，这使得真阳性率降低了很多。
- Claude Code 算不算一个不错的安全护栏工具？许多发现虽然在技术上是假阳性，却仍是不错的「护栏」建议，或看起来像是。例如，模型常常建议把一条本来已经安全的 SQL 查询参数化。虽然这不算漏洞，但它强化了代码。我们仍把这些算作假阳性，只是不如其他假阳性那么严重。不过，这些代码加固建议并不总能被信任。我们发现有几个例子，尤其是在客户端 JavaScript 代码中，AI 试图修复它认为是 DOM 操作方面的问题，结果反而破坏了代码（在我们观察到的案例中对 HTML 做了双重转义），而那里原本根本没有安全问题。
- XSS 和 SQL 注入——难以把各个组件拼起来：模型很难追踪从服务端框架到客户端组件的数据流（这是 XSS 的常见模式），也难以追踪穿过复杂应用层的数据流。它常常被静态定义的数据搞混，或者认不出服务端的净化处理。
- 重复提示词有助于获得更多结果：大语言模型的概率特性意味着，用稍有不同的方式问同一个问题，就能产生新的发现，凸显出分析的不一致性。在同一代码库上多次重复同一个提示词，给了我们不同的答案，但最终又会绕回同一批发现。
- OpenAI Codex 有时无法报告有效的 SARIF。在我们预期的 66 份报告中，有 9 份不是有效的 SARIF。我们考虑了那些文件中报告的所有发现，但它们既不是有效的 SARIF，也不是有效的 JSON。在我们试过的所有案例中，Claude Code 都没有出现这个问题。

## 相同代码、相同 AI，每次却是不同的 bug：AI 编码智能体的非确定性问题

为了探索非确定性在实践中如何体现，我们选取了其中三个应用，针对同一个安全问题——IDOR——用同一个提示词多次运行。一种模式浮现出来：每一次运行测试，AI 的发现都不一样。

在漏洞检测的语境下，这是一个重大问题。首先，作为安全工程师，理想情况下我们希望得到比「我希望模型这次搜得够彻底」更强的保证，来确信我们的代码已针对重要的漏洞类别被扫描过。

其次，间歇性地检测漏洞，会在你的安全工具或漏洞管理系统中造成不一致和噪音。例如，如果你在使用某个 SAST 平台、ASPM，或某个内部自建的系统，这些系统往往假定：当一个先前检测到的漏洞不再出现时，它就被修复了。但在大语言模型驱动的检测中，情况可能并非如此——单次扫描可能漏掉它，于是当后续扫描重新发现同一问题时，就会创建一条「新」发现，导致重复的 JIRA 工单和开发者的挫败感。

以下是我们观察到的一些具体例子：

- PY-APP-007：第一次运行中，AI 识别出一个「缺失搜索授权」的漏洞，而另外两次运行中没有这个漏洞。第二次运行标记出仅属于那一次运行的问题。第三次运行又发现了它自己独有的一组漏洞。
- PY-APP-006：类似的情况：第一次运行挖出了用户 API 中的一个漏洞，而后续几次运行则聚焦在代码库的不同部分，例如活动摘要（event abstracts）和笔记（notes）模块。
- PY-APP-002：这里的变化也许最为明显。识别出的漏洞数量从第一次运行的 3 个跃升到第二次的 6 个，然后是 11 个。每次运行都给出不同的发现，彼此只有部分重叠。

那么，背后原因是什么？我们认为关键因素就是所谓的[上下文腐化（context rot）](https://research.trychroma.com/context-rot)和[压缩（compaction）](https://docs.anthropic.com/en/docs/claude-code/costs#reduce-token-usage)。当一个 AI 智能体被要求分析整个代码库时，它面对的是海量信息：上下文腐化导致它无法从自身上下文中准确检索信息。为了应对这一点，大语言模型会使用一种有损压缩的形式（有时称为 compaction），这意味着一些更细的推理细节，比如函数名、路径等，可能在摘要过程中丢失。

可以把它想象成试图概括一部冗长复杂的小说。你会抓住主要情节，但必然会漏掉一些微妙之处和细节。同样，AI 可能会跟丢某个特定的架构模式或某条微妙的数据流，导致它在一次运行中漏掉某个漏洞，而在另一次运行中却能抓住它。我们在 PY-APP-006 中看到了一个清晰的例子：AI 提出的修复方案之一是不完整的，因为它没有复用一个已有的用户授权基类——这条关键上下文，在那次特定的运行中似乎丢失了。

这种非确定性对我们如何对待 AI 原生的 SAST 有重大影响。一方面，AI 每次都能用不同方式「思考」的能力，意味着它能探索更广泛的潜在攻击向量，很像一支视角多元的人类渗透测试团队。另一方面，它引入了一种不确定性，可能导致混乱或不当行为。

- 覆盖不完整：单次运行可能带来虚假的安全感，因为它可能漏掉某些关键漏洞，而这些漏洞本可以在后续运行中被发现。
- 缺乏可重复性：无法复现结果，使得我们难以验证 AI 的发现，也难以以一种一致、可重复的方式信任它的输出。
- 成本和时间增加：为了得到更完整的图景而需要运行多次审计，会显著增加所需的时间和计算资源。注意：传统软件一旦写好，基本上可以「免费」再次运行（硬件成本、电力等除外）。而重度依赖大语言模型的工具并非如此——在这个案例中，读入一个代码库并对其进行推理，每次扫描可能产生数十到数百美元的词元（token）成本。对当下的模型而言，这一成本可能会随时间下降，但更新的模型可能更昂贵。

## Claude Code 新的 /security-review 命令有多大效果？

Anthropic 为 Claude Code 发布了一个[新命令](https://www.anthropic.com/news/automate-security-reviews-with-claude-code)，名为 `/security-review`。它被设计用于在拉取请求（PR）上运行，检查改动的文件并提出问题，以识别特定的安全问题。[你可以在这里找到它的提示词](https://github.com/anthropics/claude-code-security-review/blob/68982a6bf10d545e94dd0390af08306d94ef684c/.claude/commands/security-review.md)。

当我们在整个代码库上运行这个命令时，我们发现它识别出的安全问题相当有限。很多时候，它找不到我们在让 Claude Code 一次只搜索某一类特定安全问题时所得到的安全问题。

我们在 PY-APP-003、PY-APP-002 和 PY-APP-008 上运行了这个命令，它在所有这些应用中总共只发现了一个 XSS，这与我们在整体实验中得到的结果截然不同。

## 回答我们的问题

让我们根据所学，重新审视最初的研究问题。

- 假阳性率/假阴性率是多少？对于直接用在真实世界代码上的原始 AI，假阳性率非常高，从对 Codex 路径遍历的最佳情况 53%、对 Claude Code IDOR 的 78%，到最差情况下 Claude Code SQL 注入的 95%、Codex SQL 注入或 IDOR 的 100% 不等。表现也因应用而异，从 PY-APP-002 中 100%（10/10）的真实 IDOR（Claude Code），到 PY-APP-007 的 0%（0/7）。在所有应用和所有报告的发现中，Claude Code 发现了 46 个漏洞（真阳性率 14%，假阳性率 86%），Codex 报告了 21 个漏洞（真阳性率 18%，假阳性率 82%）。由于我们使用的是真实应用，在这个实验中无法准确测量假阴性。我们将在接下来的博客文章中介绍测量假阴性率的方法！
- 它为何失败？我们观察到的主要弱点，是对注入类问题的代码执行缺乏深入的语义理解。模型难以处理过程间污点流和隐式流，而这正是传统 SAST 引擎通常擅长应对的东西。部分局限也来自上下文压缩和上下文腐化。我们将继续更详细地探索这些局限，并寻找缓解它们的方案。
- 脚手架和智能体工作流有多重要？它们不仅重要，而且正变得必不可少。AI 在安全评审中的未来，不是一个单一的、庞然大物般的模型，而是一个 AI 智能体系统（包括像我们案例中这样的编码智能体），它们能使用工具、对证据进行推理，并相互协作以发现和验证漏洞。虽然我们目前还没有数据来比较「使用一个能访问 Claude Code 的智能体」与「更典型的上下文工程（也就是搭建脚手架以提供所有相关代码）配合推理模型」之间的差异，但我们观察到，系统在走完一个复杂流程、并在报告安全问题的过程中做出有根据的决策的能力上，存在巨大差异。话虽如此，一个反例是 Sean Heelan 如何做了足够的上下文工程，让一个推理模型报告出了一个漏洞（8% 的概率）。我们真的很建议你读一读他的博客文章。
- 这一切的成本如何？遗憾的是，我们一直无法统一跟踪 Claude Code 和 Codex 之间的成本。Claude Code 针对所有这些漏洞和所有这些应用的总成本是 114 美元（不含为非确定性测试和 /security-review 命令而运行的开销）。

## 结论

大语言模型并不是明天就会取代人类安全工程师的银弹；事实上，在端到端发现高严重性的注入式漏洞方面，它们相当薄弱。然而，它们是一个极其强大的工具。我们的研究表明，通过理解它们的长处（上下文推理）和短处（代码的深层语义），并借助先进的静态分析引擎围绕它们构建复杂的智能体系统，我们能够创造出比以往任何工具都强大得多的新一代安全工具。
