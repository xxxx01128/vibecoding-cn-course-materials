# 规格说明已死，规格说明万岁！

### 原型是新的规格说明，而规格说明是新的……源代码？

[Ravi Mehta](https://substack.com/@ravimehta)与[Danny Martinez](https://substack.com/@dannymartinez)

2025 年 7 月 31 日

在我的职业生涯中，规格说明变得越来越短。我刚到微软时，衡量一名产品经理（PM）价值的标准是他们规格说明的分量。多年后在 Tripadvisor，我们把那位带着一份写在餐巾纸上的规格说明来参加产品评审的产品经理奉为传奇。

产品团队常常把规格说明当作文书工作——在"真正的交付工作"之前一项必要的麻烦。工程师因优雅的代码而受到称赞，设计师因漂亮的用户体验而受到赞誉。产品经理因带来影响力而获得认可。可规格说明呢？它们通常被草草赶完、扔到一边、随之遗忘。

感谢阅读《Ravi on Product》！免费订阅即可接收新文章并支持我的工作。

这一直都是个错误。在我的[产品能力工具包](https://www.ravi-mehta.com/product-manager-skills/)中，功能规格说明之所以位居首位——十二项能力中的第一项——自有其道理。它与产品交付和产品质量一起，构成产品执行的基础。

完美的执行是优秀产品管理的基础，而一份出色的规格说明就是起跑线。

如今，我们的构建方式正在改变。工程师变得越来越快——快得多。AI 可以在几分钟内把粗略的想法变成可运行的代码。瓶颈不再是构建本身，而是知道该构建什么，并让团队围绕这些需求达成一致。

突然之间，那份不起眼的规格说明不再是转瞬即逝的文书工作。它是产品管理的基石——它正在成为源代码本身。

## 为什么产品经理突然成了瓶颈

在最近的演讲[借助 AI 更快地构建](https://www.youtube.com/watch?v=RNJCfif1dPY)中，吴恩达（Andrew Ng）指出了一股前所未有的趋势：

> "我生平第一次看到管理者向我提议，产品经理的数量应该是工程师的两倍。我仍然不知道这个提议是不是个好主意，但我认为这是世界走向的一个信号。"——吴恩达

这印证了我们在[上一篇文章](https://blog.ravi-mehta.com/p/will-ai-kill-product-management)中的预测：随着工程师借助 AI 的交付速度快了许多倍，公司需要更多而非更少的产品经理来支持这些高产的工程师。

随着产品交付的加速，产品管理的其他各个环节都承受着巨大压力——理解客户需求、打造恰当的功能、验证影响力。

而所有这些压力都汇聚到一个产物上——规格说明。

## 规格说明——新的源代码

在传统的软件开发中，程序员编写人类可读的"源代码"，然后将其编译成高度优化的、机器可读的"目标代码"。"目标代码"（也称为二进制文件）是一种副产品，可以用源代码重新生成。源代码名副其实就是唯一的真相来源。

OpenAI 的 Sean Grove 提出了一个颇具挑衅性的论点。在最近的演讲[新的代码](https://www.youtube.com/watch?v=8rABwKRsec4)中，他认为，一份写得好的提示词（即规格说明）就是新的源代码。

从这个角度看，我们做 AI 开发的方式是反的。我们精心编写提示词，把意图传达给模型。AI 生成代码。然后我们留下代码，却把提示词扔掉了。

"这就好比你把源代码碎掉了，然后还非常小心地对二进制文件进行版本控制，"Grove 评论道。

想一想。在传统编程中，源代码是神圣的。源代码包含注释、结构和文档——理解与修改系统所需的一切。二进制文件只是一个下游产物。

但有了 AI，我们把这种关系颠倒了过来。我们把生成的代码当作值得保留的产物，而把规格说明——也就是提示词——当作可以随手丢弃的东西。

Grove 认为这恰恰搞反了。代码，哪怕是优雅的代码，用他的话说也只是从规格说明到代码的一次"有损投影"。就像反编译二进制文件不会还原出原始的注释和变量名一样，阅读代码也无法告诉你背后的完整意图。

然而，规格说明包含了一切。一份足够健全的规格说明可以生成"优秀的 TypeScript 代码、优秀的 Rust 代码、服务器、客户端、文档、教程、博客文章，甚至播客。"

"一份足够健全的规格说明可以生成优秀的 TypeScript 代码、优秀的 Rust 代码、服务器、客户端、文档、教程、博客文章，甚至播客。"——Sean Grove，OpenAI

更重要的是，规格说明能做到代码做不到的事：它让人类和机器围绕共同目标达成一致。Grove 简洁地表述道："一份书面的规格说明能有效地让人类达成共识，它是你用来交流、讨论、辩论、查阅并同步的载体。"

他预测道："在不久的将来，沟通最有效的人就是最有价值的程序员。说真的，如果你能有效地沟通，你就能编程。"

新的稀缺技能不是写代码，而是写出能够完整捕捉意图和价值观的规格说明。

对产品经理来说，这听起来应该很熟悉。这一直都是我们在做的事——只不过现在机器也在听了。

## 等等，原型不是早已取代了规格说明吗？

直到最近，产品生命周期还必须以规格说明（或产品需求文档、概念文档，或餐巾纸）作为起点，由此开启最初的产品线框、设计、原型制作和 MVP 开发。

传统做法让人觉得这是一种必要的麻烦。工程师构建基本的 MVP，只为把某个东西——任何东西——交到客户手里。"如果你不为产品的第一个版本感到尴尬，那你就发布得太晚了"成了金科玉律。

最近，我们构建产品的整个方式发生了重大转变，在这个新世界里，规格说明往往是输出，而非输入。

如今，你无需交付哪怕一行代码，就能把原型交到客户手中。v0、Lovable 和 Replit 等工具让你在几小时而非几周内就能构建出可运行的原型。完全不需要工程开发。

这不只是更快——而是根本上的不同。有了一个"氛围编程"出来的原型，你就能在写下功能规格说明的第一行之前收集到真实的客户反馈。你可以验证假设、迭代流程、打磨交互。

- 旧的工作流是这样的：模糊的想法 → 产品线框 → 设计 → 工程师构建的 MVP → 客户反馈 → 痛苦的规格说明修订 → 产品线框 → 设计 → 重建 → 祈祷。
- 新的工作流：模糊的想法 → 快速原型 → 客户反馈 → 清晰透彻的规格说明 → AI 辅助的实现。

原型并没有取代规格说明，而是让规格说明变得更好。

## 规格说明驱动的开发实践

让我们看一个实操案例，看看这一切是如何发生的。[Danny Martinez](https://open.substack.com/users/4227372-danny-martinez?utm_source=mentions)是 decimals 的创始人，这是一个（尚处于隐匿模式的）平台，帮助创作者经济领域的专家把其人脉中的人才推荐到工作岗位。

- 你是一位正在寻找新机会的 AI 优先产品经理吗？留下你的信息，当我们遇到有意思的机会时会通知你。
- 你是一家想招聘 AI 优先产品经理的公司吗？申请加入我们的人才网络，我们将为你提供一份精选的候选人名单。

Danny 将带我们了解他们的规格说明驱动开发流程——这一流程带来了两方面影响：

- 对于较大的功能，与工程团队的沟通得到了极大改善；
- 对于较小的功能，让此前没有任何编程经验的 Danny 也能从头到尾完成从详细规格说明到功能上线的全过程。

下面交给 Danny……

这是我最近做的一个例子。作为背景，我们正在构建一款产品，让专家型意见领袖能够把其人脉中的候选人推荐到工作岗位。在上线了一个新的落地页之后，我们需要给专家们提供一个快速访问自己页面链接的方式。

> 我们需要在页眉中加一个按钮，指向公司申请页面。我现在正忙着处理邮件相关的事情。如果你能接手的话，这个可以用氛围编程搞定。

这是来自我联合创始人的消息，说的是一个需要上线的简单按钮。足够简单，也恰恰是如今非技术人员都能自己交付的那类东西。

以下是这套配置，以及它在几分钟内就完成交付的步骤：

- 项目管理工具：Linear
- 集成开发环境（IDE）：VS Code
- 扩展：GitHub Copilot Pro
- 模型：Claude Sonnet 4
- MCP 服务器：Linear MCP 服务器，用于通过 Copilot 访问 Linear 工单

让我们来看看这个流程中的各个步骤（可以对照上面的 Loom 视频）：

- 根据我联合创始人在 Slack 中的消息生成一张 Linear 工单（00:14）
- 在上述工单中明确我想要的文案内容（00:25）
- 打开 Copilot，提示 Claude 打开那张 Linear 工单（01:18）
- 提示 Claude 审查该工单，并结合代码库对其进行分析（01:52）
- 提示 Claude 创建一个分支并实现这些改动（02:30）
- 测试这些改动，确保它们按预期工作。（02:52）
- 在 GitHub 上发起一个拉取请求（PR），将这些改动交付到代码库中（03:55）
- 等待工程师评审/批准该 PR

退一步看，这套配置的真正威力就显现出来了。是的，这只是一个简单的例子，但要点依然成立：如今，一个非技术人员借助 GitHub Copilot 向 Claude 发出几条提示词，就能在 Linear 工单、代码库和工程师之间来回穿梭。

再次强调，这一切的关键并非代码本身，而是规格说明。

现在，有必要补充说明一下，要让上述做法运转良好，需要具备哪些条件：

- 具体明确：使用模糊的规格说明只会导致代码库一团糟。借助 Claude 起草工单初稿、审查代码库并帮助使其更加具体，是这一流程中不可或缺的一环。在我们这里，还有一份关于如何写好规格说明的指南。
- 有所取舍：将上述方法用于较简单的任务最为理想。工单越复杂，就越需要一个懂行的人介入（在这些情况下，"自助服务"最终恰恰名不副实）。
- 把关审核：这种方法之所以运转良好，是因为有一位真正懂行的工程师在评审改动，确保简洁性与功能性之间的平衡得以维持。

但我们要说清楚：规则已经变了。对于参与产品构建的每一个人——包括大语言模型——规格说明都是唯一的真相来源。

有了合适的配置，作为一名非技术人员而期望能为代码库做贡献，是完全现实的。只要有足够的时间和耐心，你就能开始理解代码库并亲自实现改动，而不是每次都单纯依赖 Claude 来帮你脱困。

也许有一天，你甚至可以一边品着咖啡，一边期待 AI 智能体替你交付工单。

如果你是一名产品经理，担心 AI 会怎样影响你的工作，关键在于意识到这份工作本身正在改变。但其他人也是如此。好消息是，成为一名出色产品经理所需的核心技能，在这个新世界里反而更加宝贵。

正如我们在[之前的文章](https://hiringhumans.decimals.work/p/will-ai-kill-product-management-i)中预测的那样，采用这种方式工作的公司将需要更多而非更少的产品经理。事实证明，这个预测相当准确：

## 规格说明万岁！

创造"赛博空间"一词的科幻作家威廉·吉布森（William Gibson）曾说过：

> 未来已经到来——只是分布得并不均匀。

每当我想到 AI 能做到和做不到什么时，就会想起这句话。如今，AI 带来的进步极其不均衡。某些事情——生成代码、文本、图片——取得了飞跃式的进展，它们以 AI 的速度运行。而另一些事情——与客户交谈、发现他们的需求、说服他们购买——仍然以人类的速度推进。

这种不均衡正在重塑产品团队。聚光灯正从执行工作转向理解工作。那些始终让最优秀的产品经理脱颖而出的核心技能——理解用户需求、清晰定义问题、设计优雅的解决方案——其价值呈指数级增长。

最优秀的产品经理会把这些洞见转化为规格说明——这种规格说明能让团队达成一致、指导实施，并在日益自动化的开发世界中成为持久留存的产物。
