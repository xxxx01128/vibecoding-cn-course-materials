摘要
现代代码评审是这样一个过程：代码作者所提交的一份增量式代码贡献，在被提交到版本控制系统之前，由一位或多位同行进行评审。现代代码评审的一个重要环节，是核验代码贡献是否遵循最佳实践。虽然其中有些最佳实践可以自动核验，但另一些的核验通常留给人工评审者完成。本文报告了 AutoCommenter 的开发、部署与评估；这是一个由大语言模型驱动的系统，能够自动学习并推行编码最佳实践。我们为四种编程语言（C++、Java、Python 和 Go）实现了 AutoCommenter，并在一个大型工业环境中评估了它的性能与采用情况。我们的评估表明，一个用于学习并推行编码最佳实践的端到端系统是可行的，并且对开发者的工作流程具有积极影响。此外，本文还报告了将这样一个系统部署给数万名开发者所面临的挑战，以及相应的经验教训。

1 引言
现代代码评审[21, 23]（相较于整体性代码评审[8]）多年来在开源与工业环境中自然发展而来。现已形成一套通用的同行评审标准[5, 20, 21]，其中包括编码最佳实践。许多公司、项目乃至编程语言都以"风格指南"[1–4]的形式对其作出正式定义，通常涵盖以下几个方面：
• 格式：行长限制、空白字符与缩进的使用、圆括号与方括号的位置等；
• 命名：大小写、简洁性、描述性等；
• 文档：文件级、函数级及其他注释的预期位置与内容；
• 语言特性：在不同（代码）上下文中使用特定的语言特性；
• 代码惯用法：使用代码惯用法以提升代码的清晰度、模块化和可维护性。

开发者普遍表示对现代代码评审流程高度满意[23, 28]。其主要好处之一，是为那些不熟悉代码库、特定语言特性或常见代码惯用法的代码作者提供了学习机会。在评审过程中，专家开发者除了评审（并了解）代码贡献及其影响之外，还会向代码作者传授最佳实践。

诸如 linter[15]之类的静态分析工具能够自动核验代码是否遵循某些最佳实践（例如格式规则），有些工具甚至可以自动修复违规之处。然而，那些细微的准则或带有例外情形的准则难以被完整自动核验（例如命名约定以及遗留代码中有正当理由的偏离）；还有些准则根本无法用精确的规则加以刻画（例如代码注释的清晰度与具体性），只能依赖人的判断和开发者的集体知识。因此，人们普遍预期由人工评审者检查代码变更是否存在最佳实践违规。

代码评审流程最大的成本是所需的时间，尤其是专家开发者的时间。即便已大量采用自动化，并尽可能让流程轻量化，一名开发者每天仍可能轻易为此投入数小时[23]。机器学习的最新进展，尤其是大语言模型（LLM）的能力，表明 LLM 适合用于代码评审自动化（例如[11, 16, 17, 24–26]）。然而，围绕大规模部署端到端系统所涉及的软件工程挑战，仍有待探索。同样，针对此类系统整体效能与用户接受度的外部评估也尚付阙如。

本文研究是否有可能将代码评审流程部分自动化，具体而言是自动检测最佳实践违规，从而为代码作者提供及时反馈，并让评审者得以专注于整体功能。具体而言，本文报告了我们在 Google 的工业环境中开发、部署与评估 AutoCommenter（一个自动化代码评审助手）的经验；目前，它每天被数万名开发者使用。
总之，本文的贡献如下：
• 一种基于大语言模型的代码评审助手系统的通用架构（第 3 节）。
• 对工具校准以及向数万名开发者部署过程的描述（第 4 节）。
• 对该系统的评估（第 5 节）。
• 对经验教训的总结与讨论（第 6 节）。

2 背景
AutoCommenter 是在 Google 的大型工业环境中开发的。Google 的现代代码评审实践与其他工业界及开源项目类似[23]。

2.1 代码评审流程
Google 的代码评审流程体系成熟，以变更为基础，并借助工具辅助。Ivanković 等人[12]与 Petrović 等人[18]对该流程作了详细总结。对代码库的每一项变更都必须至少由另一名开发者评审。每天都有数以万计的代码库变更经过评审流程，数以万计的开发者以代码作者和评审者的双重身份参与其中。

作者与评审者通过代码评审系统交换意见，评审则通过受变更影响文件的快照逐步推进。每一条评审意见都附于某个特定文件快照中的具体行与列范围。为处理一条意见，作者通常会在本地副本中修改文件，并导出新的快照进入下一轮代码评审。

代码评审流程中代价最高的部分，是代码作者与评审者"照看"一项变更所花费的时间（从最初的编码，到处理评审意见并确保所有自动化分析通过，再到最终将变更合并进代码库）。尽管该流程已通过自动化系统在评审前分析代码加以优化（尤其是无需人工干预的自动代码格式化），代码评审每年仍耗费数千人年的开发工作量。因此，即便是个位数的百分比节省，也会带来显著的业务影响。

2.2 最佳实践
最佳实践是指某种被认为更优的编程语言特定用法；最佳实践文档则描述应如何使用它以及它带来何种好处。最佳实践 URL 指向某份最佳实践文档或其中的具体章节；最佳实践违规则指某段不遵循最佳实践、但可以改动以符合它的具体代码。在上下文清晰时，我们用术语"URL"和"违规"分别指代最佳实践 URL 与最佳实践违规。

Google 的中央代码仓库包含多种语言的代码，其中 C++、Java、Python 和 Go 各自都超过 1 亿行[19]。针对 15 种不同语言，都有正式的风格指南可供所有开发者随时查阅。其中许多语言还配有额外的语言入门资料、核心库文档以及"每周技巧"式的简报。虽然这些材料的执行力度不如风格指南严格，但它们在代码评审中被频繁引用。有些语言拥有多达数百页的此类文档。代码作者与评审者都被期望核验代码是否遵循所有最佳实践。

十多年前引入的一项名为"可读性"（readability）的正式机制，确保最佳实践得到一致遵循。每种语言都有专门的风格专家，称为"可读性导师"（readability mentors），他们指导经验不足的开发者熟练掌握该语言[23]。可读性导师通常用几句话概括某项最佳实践，并在评论末尾附上一个 URL，供变更作者参考。图 1 展示了一条由可读性导师发布的评论示例。

可读性流程存在一些弊端。对作者而言，额外的评审轮次增加了开发时间。对可读性导师而言，这可能变成一项单调且耗时的任务。它要求掌握数百项不断演进的最佳实践，包括识别并废弃过时规则，以及在代码评审系统中（附相关链接）将它们记录下来。此外，还需要有时经过多轮迭代的跟踪，以确保所有违规都已得到修正。

3 方法
为应对第 2.1 节和第 2.2 节所述的挑战，我们开发了 AutoCommenter——一款自动检测最佳实践违规的代码分析工具。它旨在为代码作者提供及时反馈，并减轻人工最佳实践评审的需求，从而让评审者专注于代码功能。

3.1 模型与任务定义
将最佳实践分析自动化，需要一个能够表示源代码、精确定位违规位置并识别所违反之最佳实践的模型。我们的目标是实现一种文本到文本的转换，采用基于 T5 的传统 Transformer 方法，并使用 T5X[22]。最佳实践分析是一个多任务大序列模型中的一项任务。除 T5 的标准预训练任务——跨度去噪（预测被遮蔽的词元）之外，用于训练该模型的其他任务还包括：代码评审意见处理、下一次编辑预测、变量重命名以及构建错误修复[9]。训练语料包含超过 30 亿个样本，其中最佳实践分析数据集贡献了约 80 万个样本。该模型使用此类模型典型的标准交叉熵损失进行训练，并针对序列准确率这一指标进行调优，即为每个样本预测出完全正确的目标文本。

对于最佳实践分析，模型的输入是一段任务提示词和源代码，输出目标是源代码位置以及最佳实践违规对应的 URL。任务提示词被格式化为一段固定文本的代码注释，采用相应编程语言恰当的注释风格。它以自然语言描述任务，并置于源代码之前；源代码则是某个文件的直接文本表示。若输入超出模型的上下文窗口，则会被截断。位置是源代码中的字节偏移量，URL 则指向被违反的最佳实践。目标格式由一种领域特定语言定义；若不存在违规，则有一种特殊情况，即"空"目标。除目标之外，模型还会输出一个介于 0 到 1 之间的置信度分数。

请看下面这个 Go 语言的输入/目标示例。

3.2 模型训练
图 2 展示了模型训练流水线的架构，它由三个部分组成。我们将数据集构建拆分为两个步骤（预处理与整理），因为第一步处理的数据量要大得多，成本也显著更高。预处理步骤的输出与模型的输入/目标表示无关。这种分离使得可以快速迭代样本表示及其他样本层面的调整，从而提升了特性交付速度。预处理步骤使用容错调度系统，并周期性地抽取相关代码评论，以确保新数据随时可用。

3.2.1 大规模预处理。
训练样本由真实的代码评审数据生成，但并非所有代码评论都适合用于模型训练。因此，预处理步骤会识别出相关代码评论——即包含指向最佳实践文档之 URL 的人工撰写评论。随后，预处理步骤为每条评论收集相应的源代码及相关元数据，包括该评论在源代码中的位置及其创建时间。该步骤的输出是一组相关代码评论，每一条都带有整理模型训练样本所需的全部数据。

3.2.2 数据集整理。
数据集整理是一次性的按需处理步骤，以 Beam¹ 流水线实现。它依据第 3.1 节所述的输入/目标格式，将每条相关代码评论转换为标准的 TensorFlow Example 数据结构。

3.2.3 训练与微调。
整理好的样本直接用于模型训练与评估。我们在一组 TPU 上使用 T5X 框架[22]，每 1000 步保存一次模型检查点，并使用 Tensorboard 监控训练过程。

3.3 模型选择
两项基于历史数据的内部评估为我们选择模型检查点、置信度阈值和解码策略提供了依据。首先，在验证集与测试集上的评估给出了按文件计算的精确率与召回率估计。其次，在完整历史代码评审上的评估给出了每次代码评审评论总数的估计，表明开发者与 AutoCommenter 交互的频繁程度。

3.3.1 在验证集与测试集上的评估。
我们按时间切分数据集，以确保模型未在验证集和测试集中代码评论的未来代码评审快照上接受训练。在我们的数据集中，85% 的文件恰好有一条相关代码评论，11% 有两条，4% 有三条或更多。若预测出的代码位置和 URL 与期望值相匹配（不论顺序），我们就将其定义为正确预测。

回想一下，模型会为每次预测提供一个置信度分数，这就引入了另一个参数：若某次预测的置信度分数低于某一阈值 𝑡，该预测就会被抑制。我们将 𝑃𝑟𝑒𝑐𝑖𝑠𝑖𝑜𝑛𝑡 定义为：置信度分数大于 𝑡 的正确预测数，除以置信度分数大于 𝑡 的全部预测数；𝑅𝑒𝑐𝑎𝑙𝑙𝑡 的定义与之类似。借助这些定义，我们可以估算作为 𝑡 的函数、将向用户展示多少（不）正确的结果。训练期间使用 𝑃𝑟𝑒𝑐𝑖𝑠𝑖𝑜𝑛𝑡 和 𝑅𝑒𝑐𝑎𝑙𝑙𝑡 来比较不同的模型检查点。

尽管该评估避免了数据泄露，并使我们能够自动评估模型性能，但它有一个局限：虽然可以合理假定某次代码评审快照中的人工评论是正确的，但这些评论并不详尽。换句话说，某次代码评审快照中的代码可能依据多项最佳实践都有改进空间，但人工评审者并未针对所有最佳实践都发布（附带 URL 的）评论。出现这种情况的原因可能有多种：
• 缺少引用：评审者可能对某个问题发表了评论，但未附上 URL 作为参考。
• 选择性评论：评审者可能只对某个问题评论一次，期望作者在整个代码中都加以修复。
• 专长或关注点各异：评审者可能并不熟悉所有最佳实践，或只是在某次代码评审中选择不对某个问题发表评论（例如只关注发生变更的代码）。

尽管数据集中大多数文件只有一条相关评论，但基于对"不正确"预测的手动检查所获得的经验证据表明，由于上述原因，通常可能对应多条最佳实践评论。鉴于我们的真值数据并不完整，精确率与召回率的度量带有噪声。因此，我们采用下文所述的补充性评估，以提高对模型整体性能的信心。

3.3.2 在完整历史代码评审上的评估。
为准确衡量真实环境中潜在的评论量，我们使用特定的模型检查点和阈值，在一组历史代码评审上评估 AutoCommenter。预测出的评论不会追溯性地发布到代码评审系统中，而是记录在数据库中以供分析。这使我们能够估算预期的发布频率——包括按文件和按代码评审两种粒度。由于开发者是针对一整套待评审的代码变更与 AutoCommenter 交互，因此该评估是生产部署前的重要一步。额外的好处是，这一步还便于进一步优化，并评估不同用户群体、编程语言等的发布频率。

3.4 推理基础设施
AutoCommenter 的核心是一个中央最佳实践分析服务。该服务以一个或多个源代码文件作为输入进行分析。对每个文件，它构建一个模型输入（第 3.1 节），将其编码为标准的 TensorFlow Example 数据结构，然后查询模型。模型本身由一项模型服务提供支撑，该服务使用 TensorFlow 的 Example 数据结构作为与领域无关的输入输出格式。最后，最佳实践分析服务执行一系列过滤步骤（第 4 节），抑制低质量预测，并返回剩余的预测。

3.5 集成开发环境（IDE）与代码评审的集成
开发者通过两种方式与 AutoCommenter 的分析服务交互——直接通过 IDE 插件，或间接通过代码评审系统。Google 的所有开发者都使用代码评审系统，几乎所有人也都使用 IDE。

AutoCommenter 的评论在 IDE 中以诊断信息的形式出现，用蓝色波浪下划线标出，覆盖相关的代码片段。将鼠标悬停在带下划线的代码上，会显示完整评论，其中包含对最佳实践的简明摘要，以及指向相关最佳实践文档的可点击链接。这种嵌入式信息省去了开发者为查阅不熟悉的最佳实践而在 IDE 与网页浏览器之间来回切换的需要，从而简化了工作流程。由于 IDE 中的评论需要实时生成，我们的目标是以亚秒级延迟生成评论。

在代码评审系统中，AutoCommenter 在每次更新后（即每个新的代码评审快照上）运行，一旦检测到任何违规便自动发布评论。自动化工具产生的评论在视觉上类似于人工产生的评论，但背景颜色不同。图 3 展示了 AutoCommenter 在代码评审系统中生成并发布的一条评论示例。请注意右侧的点赞和点踩按钮，作者与评审者若认为某条评论特别有用或无用，可以点击它们。另请注意左侧的"请修复"按钮，它仅对评审者可见。点击后会生成一条新评论，表明评审者认为该评论很重要，必须在代码合并进代码库之前予以处理。这些反馈按钮是代码评审系统中的标准配置，存在于所有由自动化工具生成的评论上（例如[7, 13]），并为工具的用户接受度提供了一个信号。IDE 提供了类似的反馈机制。

4.1 选择阈值与解码策略
4.1.1 阈值。
在初始部署阶段，我们希望谨慎管理开发者对 AutoCommenter 的信任，因此从一个高达 𝑡 = 0.98 的置信度阈值开始。我们手动抽样了数百条结果，发现低于该阈值的预测中约有 80% 仍然正确——也就是说，在 𝑡 = 0.98 时假阴性率非常高。此外，我们观察到 Python 的预测呈现出显著不同的置信度分数分布，其受阈值化的影响格外大。我们推测，原因在于训练数据集的构成（不同 URL 的数量及 URL 的频率）以及最佳实践文档的具体性，但将更深入的研究留待未来工作。我们曾尝试部署按语言区分的阈值，但证明无效，因为单一的语言阈值仍无法充分反映模型正确预测数百种不同最佳实践的能力。这导致预测出的 URL 缺乏多样性，因为模型倾向于给某些 URL 打出比其他 URL 更高的分数，而不论其正确性如何。这些观察促成了对 AutoCommenter 的第一次重大改动：基于验证集上的内部评估来计算按 URL 区分的阈值。

4.1.2 解码。
一项在完整历史代码评审上、采用按 URL 阈值配合贪心解码的评估显示，AutoCommenter 在 6% 的已变更文件中检测到了违规。然而，80% 的评论会发布在作者并未修改的代码行上。开发者通常不会对未变更的代码采取行动。因此，AutoCommenter 会过滤掉针对未变更代码行生成的评论，使已变更文件中的评论比例降至 1.3%。为提高这一比例，我们试验了不同的解码策略：贪心（默认）、束搜索、top-k 采样和 top-p 采样。我们最终选用束搜索（生成 𝑛 = 4 个候选响应），使发布频率提高三倍，达到 3.9%。它还显著提升了 URL 的多样性：发布最频繁的 10 个 URL 占全部评论的 41%，而贪心搜索下这一比例为 80%。

在为部署选择解码策略时，延迟是另一个重要方面。虽然束搜索提高了发布频率和多样性，但推理明显变慢（中位延迟为 2 秒）。鉴于这一延迟对于 IDE 中的交互式使用而言难以接受，我们最终决定在代码评审系统中使用束搜索，在 IDE 中使用贪心搜索。

4.2 抑制过时的最佳实践
在向约 3000 名自愿的首批采用者推出 AutoCommenter 后，我们注意到几天之内用户就提交了大量问题报告。其中许多都指向同一个 URL²，它描述的是与 Python 导入相关的最佳实践。然而，某些类型名称的规范来源在 Python 3.9 中发生了变化，该最佳实践也在 2022 年初发生了改变。由于我们的训练数据早于 2022 年，其中包含了若干已不再适用的最佳实践评论。我们意识到这是一种反复出现的模式：随着语言演进或新库的引入，最佳实践也在不断演进。缓解该问题的一种方法是（在规则变化时）过滤掉此类数据并重新训练模型。然而，这既耗时又耗资源：它需要完整地重新生成数据、训练模型、评估并上线。在此期间，要么关闭"过时"的模型，从而导致系统停机；要么抑制受影响的预测。否则，系统可能很快失去开发者的信任。我们选择抑制特定的最佳实践预测，并采用条件过滤（在源代码上匹配正则表达式），原因有二。首先，它可以动态部署并立即生效。其次，它允许对预测进行细粒度的过滤。

4.3 对所选评论的独立评分
经过数月的早期使用，我们观察到有用率在 54% 左右停滞不前。为理解原因、找出改进方向并为更广泛的部署做准备，我们于 2023 年 4 月开展了一项独立的人工评分研究，分析了约 370 条在首批采用者部署期间收到开发者反馈的已发布评论样本。

为收集关于评论有用性的多元视角，我们招募了 15 名评分者——来自合作团队的开发者。我们请他们对收到明确用户反馈的 AutoCommenter 评论进行评分。我们未向评分者展示原始的用户反馈，以避免对其评估产生偏差。评分者根据所链接的最佳实践及周边代码来评估每条评论的有用性。我们要求他们重点关注评论的正确性，同时也考虑该评论对他们作为作者而言是否可操作（例如，他们是否会处理一条技术上正确、但在特定情形下似乎不值得处理的评论）。我们鼓励他们对每条评论提供开放式反馈。

评分者评估得出的有用率为 60%，略高于同一批评论在开发者反馈中的 54%，但远低于我们为更广泛部署设定的 80% 目标。这项研究最有趣的发现是，无用评论存在清晰可辨的模式。以下是一些例子：

多个主题或复杂主题：例如，有一个 URL 指向某一节，其中描述了与 Python linter 交互的多条准则，包括它经常触发的情形以及抑制它的方法。作者可能难以理解某条已发布评论所指的是哪条具体准则，以及该如何处理它。类似地，关于如何在 C++ 中撰写良好函数文档的指南是一整页密密麻麻的文字。评分者频繁指出，最佳实践（以及 AutoCommenter 的简明摘要）与实际代码之间存在脱节，即便代码中确实存在相关违规也是如此。
2https://github.com/google/styleguide/blob/gh-pages/pyguide.md#22-imports

高质量摘要的重要性：评分者常常发现，AutoCommenter 的摘要是通过抓取文档源生成的，有时会缺失，因而未能充分解释所引用准则与评论/代码之间的关联。

主观且可能有争议的主题：一个例子是避免在库代码中使用标志位（flags）。标志位在库中使用时可能引发问题，但有些库恰恰是专为通过标志位配置大量特性而设计的。此外，遗留代码可能不遵循这一准则，而评审者也不会强制要求。模型没有学到这些细微差别，有时会在作者向现有库添加新标志位时预测为违规。

某些准则上的系统性模型错误：一个有趣的例子是一条准则，它提倡在 C++ 的 vector 中使用成员函数 push_back 而非 emplace_back，因为两者用相同参数即可达到相同效果。模型学会了预测这一点，但它也会在 emplace_back 确实更合适的场景下做出同样预测，甚至在不相关的类型拥有名为 push_back 的成员函数时也是如此。

正确但价值低的评论：代码注释中句子末尾缺少句号，通常会被人工评审者所允许。虽然技术上正确，但要求作者回到 IDE 去修复这一问题，可能带来净负面价值。

评分者研究所得的洞见促成了对 AutoCommenter 的两项改动。首先，评分者研究识别出 17 个不可操作的 URL；抑制它们后，按开发者反馈计算的历史有用率从 54% 提升至 66%，按评分者反馈计算则从 60% 提升至 74%。我们进一步分析了链接到类似但未评分 URL 的评论，又额外抑制了 5 个。其次，我们审查并手动更新了所有频繁发布 URL 的摘要。这些改动合在一起，足以使我们在下一部署阶段达到 80% 的有用率目标。

4.4 A/B 实验
2023 年 7 月，我们在一项 A/B 实验中将 AutoCommenter 部署给了约半数开发者。我们将开发者随机分配到实验组（启用 AutoCommenter）和对照组（禁用 AutoCommenter）。我们依据开发者电子邮件地址的 SHA256 哈希值的末几位进行随机分组，并核实两组在规模和构成上没有差异，包括任职年限、资历、编程语言和业务部门的分布。我们还确认，在实验开始之前，实验期间测量的各项变量在对照组与实验组之间均无差异。实验期间的评论发布频率与预期一致（第 4.1 节）。

我们在以下各项中均未检测到任何统计显著的变化：代码评审的总时长、开发者在代码评审上实际花费的时间、作者与评审者之间评论—回应的往返次数。不过，我们确实检测到编码速度略有提升。我们推测，这一积极效果源自因查阅文档而发生的上下文切换有所减少。我们将更深入的研究留待未来工作。基于这些结果，我们得出结论：不存在负面影响，并于 2023 年 10 月将 AutoCommenter 部署给了所有开发者。

5 评估
基于自 2023 年 3 月以来收集的有用率与用户反馈，我们得出结论：开发者总体上对 AutoCommenter 产生的评论感到满意。我们通过分析用户反馈，持续改进数据集准备、阈值设定、URL 抑制与摘要生成，以确保 AutoCommenter 对开发者的工作流程带来高度积极的影响。

除开发者满意度之外，在面向 Google 全员广泛发布数月之后，我们还评估了 AutoCommenter 性能的另外三个方面：
（1）评论处理：开发者有多大频率会修改代码以处理 AutoCommenter 发布的评论？
（2）AutoCommenter 与人工评论的对比：AutoCommenter 的评论在多大程度上覆盖了人工评审者在其评论中引用的最佳实践文档？
（3）AutoCommenter 与 linter 的对比：AutoCommenter 的输出在多大程度上超越了传统静态分析工具的能力？

5.1 评论处理
开发者很少通过点击代码评审系统和 IDE 中的点赞/点踩按钮，以及代码评审系统中的"请修复"按钮（图 3），对 AutoCommenter 的评论给出明确反馈：代码评审系统中约 10% 的自动化评论和 IDE 中 2% 的诊断信息收到了明确反馈，这与 Google 其他自动化分析的情况相当。与此同时，开发者会将鼠标悬停在约 50% 的 AutoCommenter IDE 诊断信息上；此前的研究表明，开发者常常在没有明确反馈的情况下就处理了自动化评论[18]。为评估开发者处理 AutoCommenter 评论的频率，我们开展了一项离线分析，估算由后续代码变更所处理的评论比例。

为分析评论处理情况，我们提取了以含有 AutoCommenter 自动化评论的文件为重点的历史变更。对每一项变更，我们提取了发布评论时的初始快照，以及开发者最终合并进代码库的快照。每条评论都覆盖特定的行范围。我们在这些快照之间使用了一种基于抽象语法树（AST）的自动行映射方法[18]，以识别出模型在初始快照上原本预测了、但在合并后的快照上未再预测的评论。这样的快照对表明某条评论可能已被处理，但也有可能是无关的代码变更导致某条特定评论不再被预测。

对 6000 对快照的自动分析显示，在 50% 的情况下，该评论在提交快照中原先发布的行上已不复存在。我们随机抽取了 40 对这样的快照进行人工检查。我们发现，在 80% 的情况下，作者所做的变更直接解决了已发布评论所描述的问题。因此，我们估计评论处理率约为 40%，这显著高于带明确正面反馈的评论在所有评论中所占的比例。

5.2 AutoCommenter 与人工评论的对比
图 5 比较了 AutoCommenter 在生产环境中生成的自动化评论与训练数据中人工评论的评论累计分布（按指向最佳实践文档的唯一 URL 统计）。横轴是 URL 的排名，即将自动化评论中使用过的所有 URL 按频率排序后的名次。例如，使用最频繁的 URL 排名第 1，占全部自动化评论的 9.9%。同一 URL 在训练数据中人工撰写的评论里出现了 4.3%。总计，AutoCommenter 已针对 330 个不同的 URL 生成过评论。AutoCommenter 使用的 URL 集合覆盖了 68% 带有最佳实践 URL 的历史人工评论。这是一个不错的成果：它表明 AutoCommenter 并未聚焦于评审者很少引用的冷门最佳实践。另一方面，尽管采用了束搜索，URL 的多样性仍然相对较低。排名前 85 的 URL 占了 AutoCommenter 所生成评论的 90%。同一组 URL 覆盖了 35% 带最佳实践 URL 的人工评论。在保持准确性与低延迟的同时，提高自动化评论中 URL 的多样性以及对最佳实践的覆盖率，是我们的首要任务之一。

6 经验教训
基于我们开发和部署 AutoCommenter 的经验，我们总结了几点关键的经验教训：
• 对传统分析的补充：AutoCommenter 由大语言模型驱动的方法，为人工评审者经常引用的 68% 的最佳实践生成了评论。其中许多都超出了传统静态分析的范围。
• 内部评估与现实世界表现：内部评估与现实表现可能显著背离：我们的内部评估使用了真实世界人工评论数据集，并配合当时最先进的模型架构与训练流程，显示出一个很有前景的模型；但事实证明，我们的外部评估与系统改进对于成功部署至关重要。
• 监控用户接受度至关重要：即便只有少数负面用户体验，也会侵蚀用户对自动化系统的信任。持续监控并分析真实世界反馈，对于发现此类情形并找出补救办法至关重要。就 AutoCommenter 而言，一个简单的抑制机制就足以在不显著牺牲效能的情况下，将用户接受度大幅提升到 80% 以上。

7 相关工作
Johnson[15] 早在 1977 年、将近 50 年前就引入了 C linter。在这 50 年间，关于自动化静态分析产生了大量研究成果：Heckman 与 Williams[10]近期的一篇文献综述识别出 17571 篇论文。许多研究探讨了开发者如何与静态分析交互。Johnson 等人[14]探讨了开发者在尝试使用静态分析时所面临的挑战。他们的研究结果凸显了良好地集成到现有开发者工作流程中的重要性，以及建立并维持对工具的信任的重要性。Vassallo 等人[27]探讨了开发者在不同情境（包括编码和代码评审）下如何与静态分析交互。他们同样发现，融入现有工作流程对开发者使用工具的意愿起着重要作用，而结果的高质量也极为关键。Beller 等人[6]研究了大量开源项目中静态代码分析的使用情况。在其他发现中，他们强调自动化分析的实际使用方式以及应有的使用方式会因编程语言而异。

相比之下，将机器学习用于代码分析是一个相对较新、理解也较少的领域。近期有若干出版物（例如 Hong 等人[11]、Li 等人[16]、Li 等人[17]、Thongtanunam 等人[24]、Tufano 等人[25]以及 Tufano 等人[26]）报告了模型评估，并提出了用于自动化代码评审的工具。尽管这些模型及评审意见生成任务与本文提出的模型非常相似，但其评估主要集中于历史数据集。如第 3.3.1 节所述，仅基于历史评论的内部评估存在一定局限，有时无法预测现实世界的表现。Frömmgen 等人[9]的另一篇近期出版物呈现了对一个线上系统的评估，但针对的是相反的任务：从评论生成代码，而非从代码生成评论。

8 结论
核验代码是否遵循最佳实践，是现代代码评审流程中的一项常见任务。虽然某些最佳实践可以借助 linter 等传统工具自动核验，但许多最佳实践需要经验丰富开发者的知识与判断，而这需要投入时间和精力。

本文报告了我们开发、部署与评估 AutoCommenter（一个由大语言模型驱动的代码评审助手系统）的经验。具体而言，本文完整呈现了从任务与模型设计、内部评估与系统校准，到分阶段上线和最终用户评估的全过程。

评估结果表明，开发一个能力远超传统工具、同时又能获得高度最终用户接受度的端到端系统是可行的。这些结果是朝着部署复杂代码评审助手与自动化代码评审迈出的有前景的第一步。

我们的首要任务是通过将 AutoCommenter 设计得具有非常高的精确率，来确保积极的开发者体验。虽然召回率并非主要关注点，但我们认识到它的重要性，并计划探索对模型和系统架构做出哪些改动可以提升召回率。例如，我们在 2022 年使用的模型在当时是最先进的。然而，它的上下文窗口仅为 2048 个词元，只够容纳约 200 行代码。当前最先进的模型在训练时的上下文窗口达数万个词元，在推理时更超过一百万个词元。这一飞跃为新增特性以及显著改进现有特性创造了机会。
